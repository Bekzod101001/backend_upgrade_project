## Разобрался — что показал checkpoint

### Вопрос 1 (lost update) — ответ частично точный

Мой ответ: «два вызова могут перезатереть результат друг друга, Б забивает на изменения А и юзает актуальную на тот момент запись».

Механизм верный в общих чертах, но упущено главное: это конкретно **read-modify-write** паттерн, а не просто «два процесса трогают одну запись».

```
balance = 1000
T1: SELECT balance → 1000
T2: SELECT balance → 1000        (READ COMMITTED это разрешает — не dirty read, но и не защита от staleness)
T1: balance - 100 = 900 → UPDATE balance = 900, COMMIT
T2: balance - 200 = 800 → UPDATE balance = 800, COMMIT   ← T1's -100 ПОТЕРЯНО
итог: 800, должно быть 700
```

Уточнение, которого не хватило в ответе: READ COMMITTED гарантирует только отсутствие dirty read (не читать незакоммиченное). Он НЕ проверяет на UPDATE, что строка не изменилась с момента SELECT в этой же транзакции. Именно эту дыру закрывает `FOR UPDATE` (Day 4) или `@Version` (ещё не реализован в MiniBank, в LEARN-LATER).

**Себе на повторение:** проговорить это ещё раз через неделю-две, акцент на "read-modify-write" и на том, что именно READ COMMITTED пропускает, а не только "два процесса".

### Вопрос 3 (почему deadlock без сортировки id — гарантирован) — механизм верный, но всплыла реальная ошибка интуиции

Сам deadlock (AB-BA lock ordering conflict) описан верно: первый вызов лочит Алису, хочет Боба; второй лочит Боба, хочет Алису — оба ждут друг друга вечно.

**Ошибка, которая всплыла попутно и оказалась важнее самого вопроса:** предположение, что вероятность такого совпадения "на уровне встречи двух одинаковых UUID" — то есть астрономически редкая, почти нереальная.

Это неверно, и разница — на много порядков:

- **UUID collision** — фиксированная глобальная константа (122 случайных бита, ~2.7 квинтиллиона UUID для 50% шанса), не растёт от частоты использования.
- **Deadlock rate** — прямо пропорционален СВОЕЙ частоте транзакций на горячей паре записей. Окно конфликта — весь промежуток между "взял первый lock" и "взял второй lock" у обеих транзакций, не точка во времени.

Собственное же доказательство было в Day 4 и оказалось забыто в моменте:
```
=== opposite transfers === (до фикса)
errors: 18   (из 20 параллельных вызовов)
[CannotAcquireLockException <- ERROR: deadlock detected]
```
18 из 20 — не "редкий случай", а систематический эффект при любой заметной нагрузке на встречные переводы одной пары счетов. У deadlock в Postgres даже свой код ошибки (`40P01`), и retry-логика под него — стандартная часть любого serious ORM/фреймворка.

**Формула на повторение:** вероятность deadlock масштабируется с собственной нагрузкой на горячие данные — это НЕ фиксированная астрономически малая константа, как коллизия UUID. Разные классы вероятности, нельзя сравнивать интуицией "оба маленькие числа".

Побочный вопрос, поднятый в моменте (не разобран подробно, интересно, но не по теме): если бы два случайных UUID реально столкнулись — это было бы отслежено/зафиксировано? Короткий ответ — да, скорее всего означало бы баг в генераторе случайных чисел, а не настоящую случайную коллизию; не относится к оценке checkpoint, оставлено как любопытство.

### Вопрос 2 (pessimistic vs optimistic lock) — направление верное, но две реальные неточности

Мой ответ: «pessimistic исходит из того что транзакции важны и ждут друг друга, optimistic опирается на версионирование, остальные транзакции просто падают от конфликта — pessimistic не теряет транзакции, optimistic хотя бы падает понятно».

**Неточность 1 — «pessimistic исходит из важности транзакций».** Дело не в важности, а в **предполагаемой вероятности конфликта**: pessimistic предполагает, что конкуренция за запись частая, поэтому дешевле заблокировать заранее, чем потом откатывать.

**Неточность 2, более серьёзная — «pessimistic не теряет никакие транзакции».** Это прямо противоречит тому, что только что разобрали в вопросе 3: pessimistic lock тоже роняет транзакции, просто другим путём:
```
Pessimistic:  конфликт → ВТОРАЯ транзакция ЖДЁТ
              → ждёт слишком долго → lock_timeout → ошибка
              → ждёт по кругу → DEADLOCK → CannotAcquireLockException
Optimistic:   конфликт → транзакция НЕ ждёт вообще
              → на UPDATE обнаруживает несовпадение версии → OptimisticLockException
```
Разница не «падает / не падает» — падают оба, разница в том, **когда и как**: pessimistic сначала заставляет ждать (и это ожидание при неправильном порядке lock'ов — тот самый deadlock из вопроса 3), optimistic не ждёт и сразу отбивает на записи.

**Механизм optimistic lock, которого не хватило:**
```sql
UPDATE accounts SET balance = 900, version = version + 1
WHERE id = 1 AND version = 5   -- условие на СТАРУЮ версию, прочитанную при SELECT
```
Если версия успела вырасти — `UPDATE` вернёт 0 affected rows, Hibernate сам превращает это в `OptimisticLockException`. Никакого lock'а на уровне БД нет вообще, ни на `SELECT`, ни во время «раздумий» между чтением и записью.

**Критерий выбора, который не прозвучал:**
- Время между чтением и записью: перевод — миллисекунды → pessimistic ок; веб-форма, где юзер 5 минут думает перед Submit → держать `FOR UPDATE` 5 минут невозможно → только optimistic.
- Ожидаемая частота конкуренции за конкретную запись: горячие счета при параллельных переводах → pessimistic оправдан; редко изменяемая запись (профиль раз в год) → optimistic дешевле.

### Вопрос 4 (сценарий без явного lock'а вообще) — верное направление, не хватило точной трассы

Мой ответ: Боб (баланс 100) «случайно» переводит 100 дважды, если транзакция не закончилась — есть вероятность перевести Алисе суммарно 200 при балансе 100.

**Проблема 1 — смешаны два разных бага.** «Боб случайно кликнул дважды» — это double submit / отсутствие идемпотентности (Day 5, другая тема). Race condition из-за отсутствия lock'а не требует дубля вообще — деньги теряются даже если оба перевода легитимные, независимые, разным людям.

**Проблема 2 — не хватило точной трассы SELECT/UPDATE с числами**, именно это спрашивал вопрос:
```
Bob.balance = 100

T1: Bob → Alice, 100         T2: Bob → Carol, 80   (два РАЗНЫХ легитимных перевода, не дубль)

T1: SELECT bob.balance → 100          (в памяти: 100)
                              T2: SELECT bob.balance → 100   (T1 ещё не закоммитил — T2 видит те же 100)
T1: check 100 >= 100 → OK, newBalance = 0, UPDATE, COMMIT
                              T2: check 100 >= 80 → OK (T2 не видел UPDATE от T1!)
                              T2: newBalance = 100-80 = 20, UPDATE, COMMIT

Итог: Bob.balance = 20   (должно быть -80 / второй перевод обязан был упасть с InsufficientBalanceException)
Alice получила 100, Carol получила 80 → ушло 180 при балансе 100
```
Ключевая фраза для интервью: T2 прочитал баланс ДО коммита T1 — READ COMMITTED это разрешает легально, изоляция не нарушена. Проверка `if (fromAccount.getBalance() < amount)` в `TransferExecutor` читает значение из памяти Java-объекта на момент SELECT, а не актуальное состояние БД на момент UPDATE — в этом вся дыра. Ровно то, что ловит `TransferConcurrencyTest` из Day 1 (там 10 потоков делают одинаковый перевод, поэтому механизм чуть замаскирован повторяемостью суммы — с разными суммами утечка видна однозначно).
