### Разобрался

- **Слои:** `findById` принадлежит Spring Data (`CrudRepository`). Его реализует `SimpleJpaRepository`, который вызывает `EntityManager.find` (JPA), а тот реализован в `SessionImpl` (Hibernate), дальше JDBC.
- **Почему JPA отдельно от Hibernate:** это наследие Java EE, где на каждую область был стандарт и несколько вендоров (JDBC, Servlet, JMS, JPA). JPA 1.0 (2006) стандартизировал идеи Hibernate. В PHP такого стандарта нет, поэтому Doctrine и Eloquent независимы.
- **Hibernate ≈ Doctrine** (Data Mapper + Unit of Work), **Eloquent = Active Record**. Методы «из воздуха» (`findByOwnerName`) даёт Spring Data, а не Hibernate.
- **За что хейтят Hibernate:** N+1, `LazyInitializationException`, неявные UPDATE, непредсказуемый flush, скрытый SQL. Это толстая абстракция, которая протекает.
- **Шкала альтернатив:** JDBC → JdbcClient → MyBatis → jOOQ → Spring Data JDBC → Hibernate. jOOQ не ORM: схема БД — источник истины, из неё генерируется типобезопасный SQL DSL, persistence context и dirty checking нет. Для целевых вакансий JPA обязателен, остальное как плюс.
- **Зачем транзакция, если «между save'ами ничего нет»:**
  - каждый `save()` без `@Transactional` коммитится сам, и первый UPDATE уже навсегда в базе;
  - падает чаще приложение (deploy, OOM, сеть), а не Postgres;
  - второй UPDATE может упасть при живой базе: deadlock, lock timeout, `@Version`, constraint;
  - при миллионе переводов «один на миллион» случается каждый день;
  - атомарность — свойство бизнес-операции, а не страховка текущих строк кода;
  - одна транзакция дешевле четырёх.
- **Транзакция НЕ защищает от конкурентных переводов** (lost update), для этого нужны isolation и locking.
- **Dirty checking:** Hibernate хранит снимок загруженной entity и при flush сравнивает с ним, если есть отличия, генерирует UPDATE. Работает только для managed entity внутри транзакции.
- **Commit:** SQL `COMMIT`. В Spring его отправляет прокси `@Transactional` при нормальном выходе из метода, при `RuntimeException` делает rollback. Внутри commit сначала flush (отправка UPDATE), потом `COMMIT`. Грабли: checked exception по умолчанию коммитит, self-invocation идёт мимо прокси, проглоченное исключение приводит к commit.

### 4 базовых правила (минимум для задачек на собесе)

1. Без `@Transactional` каждый вызов репозитория — отдельная мини-транзакция, результат сразу в базе.
2. С `@Transactional` весь метод — одна транзакция, commit на выходе из метода.
3. `RuntimeException` откатывает всё.
4. Внутри транзакции Hibernate сам сохраняет изменения загруженных объектов, `save()` не нужен.
