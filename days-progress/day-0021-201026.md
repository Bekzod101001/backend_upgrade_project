## Конспект: жизненный цикл HTTP-запроса — завершение

Путь HTTP-запроса от браузера до Spring Boot и обратно.

### Общая последовательность

```
Пользователь вводит URL
        ↓
DNS — определение IP-адреса сервера
        ↓
Определение маршрута через таблицу маршрутизации
        ↓
ARP — получение MAC-адреса следующего узла
        ↓
Передача данных через локальную сеть и маршрутизаторы
        ↓
NAT/PAT — трансляция адреса и порта
        ↓
TCP — установление соединения
        ↓
TLS — установка защищённого соединения
        ↓
HTTP — отправка запроса
        ↓
Nginx — Reverse Proxy
        ↓
Tomcat — приём запроса в Spring Boot
        ↓
DispatcherServlet
        ↓
HandlerMapping
        ↓
Controller → Service → Repository
        ↓
Database
        ↓
HTTP Response
        ↓
Браузер
```

Это логическая схема, а не строго универсальный порядок всех сетевых операций: DNS-запрос сам требует сетевого взаимодействия, а TCP-соединение и TLS-сессия могут повторно использоваться.

### DNS и DHCP

DNS преобразует доменное имя в IP-адрес (`example.com → 93.184.215.14`). DHCP автоматически предоставляет устройству IP-адрес, маску подсети, шлюз по умолчанию и адрес DNS-сервера. DNS-сервер необязательно `8.8.8.8` — его адрес может предоставляться маршрутизатором или провайдером.

### IP, MAC и ARP

IP-адрес — логический адрес назначения пакета. MAC-адрес — доставка кадра в пределах локального сетевого сегмента. Если сервер за пределами локальной сети, устройство отправляет кадр на MAC-адрес следующего узла (обычно домашний маршрутизатор). ARP определяет MAC-адрес по известному IPv4-адресу в локальной сети. Маршрутизаторы последовательно пересылают IP-пакеты к сети назначения; MAC-адреса меняются на каждом участке пути, IP-адрес назначения обычно остаётся прежним.

### NAT/PAT

Домашние устройства обычно используют частные IP (`192.168.1.10:51000`, `192.168.1.11:51000`). При выходе в интернет маршрутизатор преобразует их в один публичный IP с разными портами (`203.0.113.10:61001`, `203.0.113.10:61002`). PAT позволяет нескольким устройствам делить один публичный IP, различая соединения по портам; маршрутизатор хранит соответствия, чтобы направлять ответные пакеты нужным устройствам.

### TCP

```
Client → SYN → Server
Client ← SYN-ACK ← Server
Client → ACK → Server
```

Three-Way Handshake. Разобраны: Sequence Number (нумерация байтов), Acknowledgment Number (подтверждение получения), Retransmission (повторная передача потерянных данных), причины потери пакетов. Вывод: IP отвечает за доставку пакетов без гарантии результата, TCP обеспечивает надёжный упорядоченный поток байтов между конечными узлами.

### TLS и HTTPS

TLS обеспечивает шифрование, проверку подлинности сервера (сертификат) и контроль целостности сообщений. Разобран принцип Diffie–Hellman Key Exchange: стороны согласуют общий секрет через обмен публичными значениями, не передавая сам секрет по сети (упрощённый математический пример на малых числах). Разобрано различие между ключами для согласования секрета и ключом сертификата для аутентификации. Уточнение: HTTP/3 использует QUIC поверх UDP, а не обычное TCP-соединение.

### Nginx как Reverse Proxy

```
Browser
   ↓
Nginx :443
   ↓
Spring Boot :8080
```

или маршрутизация по пути: `/api/* → Spring Boot :8080`, `/* → Frontend :3000`. Reverse Proxy ≠ HTTP Redirect: при проксировании Nginx сам отправляет запрос внутреннему серверу и возвращает клиенту ответ; при redirect сервер говорит браузеру отправить новый запрос по другому адресу.

### Spring MVC и обработка запроса

```
Tomcat
   ↓
DispatcherServlet
   ↓
HandlerMapping
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Tomcat — веб-сервер и Servlet Container, принимающий HTTP-запросы. `DispatcherServlet` — центральный компонент Spring MVC, координирующий обработку. `HandlerMapping` определяет подходящий обработчик по маршруту и условиям:

```java
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    return userService.findById(id);
}
```

`GET /users/123` попадёт в этот метод; `POST /users/123` не соответствует `@GetMapping` → `405 Method Not Allowed`, если маршрут существует, но HTTP-метод не поддерживается.

Аналогия с Laravel: `public/index.php → Router → Controller` ↔ `Tomcat → DispatcherServlet → HandlerMapping → Controller`.

## Конспект: Spring AOP Proxy, `@Transactional`, self-invocation, exceptions

### Spring AOP и Proxy

Spring AOP (Aspect-Oriented Programming) добавляет методам дополнительное поведение без вставки его вручную в бизнес-логику: `@Transactional` (транзакции), `@Cacheable` (кеширование), `@Async` (асинхронность), `@PreAuthorize` (права доступа).

При стандартном использовании Spring создаёт прокси-объект, через который проходят внешние вызовы методов бина:

```java
@Service
public class BankService {
    @Transactional
    public void withdraw() {
        // UPDATE accounts
    }
}
```

Концептуальная иллюстрация прокси (реально Spring использует транзакционные перехватчики и `PlatformTransactionManager`):

```java
public class BankServiceProxy {
    private final BankService target;
    public void withdraw() {
        beginTransaction();
        try {
            target.withdraw();
            commit();
        } catch (RuntimeException e) {
            rollback();
            throw e;
        }
    }
}
```

Главный вывод: `@Transactional` не вставляет `BEGIN`/`COMMIT` в тело метода — транзакционная логика выполняется через Spring Proxy.

### Self-invocation

Self-invocation — вызов объектом собственного метода:

```java
@Service
public class BankService {
    public void transfer() {
        withdraw();          // эквивалентно this.withdraw()
    }
    @Transactional
    public void withdraw() {
        // UPDATE accounts
    }
}
```

Путь вызова при `bankService.transfer()` снаружи:

```
Controller
    ↓
BankServiceProxy.transfer()
    ↓
BankService.transfer()
    ↓
this.withdraw()
```

Внутренний вызов `withdraw()` не проходит через транзакционный перехватчик Proxy → `@Transactional` на `withdraw()` не сработает при таком вызове. Прямой внешний вызов `bankService.withdraw()` через Proxy активирует транзакцию как обычно.

**Практическое правило:** аннотацию ставят на публичный метод, представляющий целую бизнес-операцию:

```java
@Service
public class BankService {
    @Transactional
    public void transfer() {
        withdraw();
        deposit();
    }
    private void withdraw() { /* списание */ }
    private void deposit() { /* зачисление */ }
}
```

При внешнем вызове `transfer()` транзакция открывается один раз, оба приватных метода выполняются внутри уже открытой транзакции — им не нужна собственная `@Transactional`.

### Байткод Java (контекст для понимания Proxy)

```
.java → javac → .class (байткод) → JVM → исполнение
```

JVM интерпретирует байткод или компилирует его в машинный код через JIT. Стандартный Spring AOP не переписывает тело бизнес-метода — используется прокси-объект. Альтернатива — AspectJ weaving: изменяет байткод и может перехватывать даже внутренние вызовы.

### Транзакции и Atomicity

```java
@Transactional
public void transfer() {
    withdraw();
    deposit();
}
```

Если `withdraw()` списал деньги, а `deposit()` выбросил `RuntimeException`, вышедший за пределы метода:

```
BEGIN → withdraw() UPDATE -100 → deposit() RuntimeException → ROLLBACK
```

Списание отменяется — проявление Atomicity из ACID.

### Влияние try-catch на транзакции

```java
@Transactional
public void transfer() {
    withdraw();
    try {
        deposit();
    } catch (RuntimeException e) {
        System.out.println("Ошибка зачисления");
    }
}
```

Если исключение из `deposit()` перехвачено внутри `transfer()`, метод завершится нормально — транзакционный перехватчик не увидит необработанного исключения и выполнит `COMMIT`. Списание может сохраниться несмотря на ошибку зачисления — опасно для финансовых операций. (Исключения из этого правила: транзакция может быть ранее помечена rollback-only, либо ошибка БД делает её непригодной для коммита.)

Чтобы обеспечить откат — пробросить исключение дальше:

```java
@Transactional
public void transfer() {
    withdraw();
    try {
        deposit();
    } catch (RuntimeException e) {
        log.error("Ошибка перевода", e);
        throw e;
    }
}
```

Теперь исключение достигает перехватчика и Spring выполняет rollback.

### Checked и Unchecked Exceptions

**Checked** — компилятор требует `try-catch` либо `throws` (`IOException`, `SQLException`, `FileNotFoundException`):

```java
public void test() throws Exception {
    throw new Exception("Ошибка");
}
```

`throws` не выбрасывает исключение, а объявляет возможность его возникновения.

**Unchecked** — компилятор не требует обработки (`RuntimeException`, `NullPointerException`, `IllegalArgumentException`, `IllegalStateException`):

```java
public void withdraw() {
    throw new RuntimeException("Недостаточно денег");
}
```

Иерархия:

```
Throwable
│
├── Error                    (unchecked)
│
└── Exception
    │
    ├── IOException          (checked)
    ├── SQLException         (checked)
    │
    └── RuntimeException     (unchecked)
        │
        ├── NullPointerException
        ├── IllegalArgumentException
        └── IllegalStateException
```

Главное отличие — что проверяет компилятор; обе категории можно перехватывать через `try-catch`.

### Exceptions и `@Transactional`

| Ситуация | Поведение |
|---|---|
| Метод завершился нормально | COMMIT |
| Вышел `RuntimeException` | ROLLBACK |
| Вышел `Error` | ROLLBACK |
| Вышло checked exception | COMMIT по умолчанию |
| Исключение обработано внутри метода | Обычно COMMIT, если транзакция не помечена для отката |

Поведение можно изменить: `@Transactional(rollbackFor = IOException.class)` — тогда checked-исключение тоже вызовет rollback.

### Что удалось понять

Назначение Spring Proxy; почему `@Transactional` реализуется через проксирование; self-invocation и почему внутренние вызовы обходят Proxy; почему приватные методы участвуют в уже открытой транзакции; влияние `RuntimeException` на rollback; почему перехват исключения через `try-catch` может привести к COMMIT; байткод Java; базовое отличие checked/unchecked; почему `throw new Exception(...)` требует `throws` или `try-catch`.
