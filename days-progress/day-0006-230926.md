## Разобрался

### Проблема, ради которой брокер вообще появляется

```java
@Transactional
public void execute(...) {
    // lock'и по порядку id (Day 4)
    from.setBalance(...); to.setBalance(...);
    smsGateway.send(...);       // ← HTTP наружу, 8 секунд
}                                // commit — только здесь отпускаются lock'и
```

Одна строка обнуляет всю работу Day 3–4: lock'и на строках Alice и Bob держатся всё время HTTP-запроса, connection из Hikari занят 8 секунд, пул кончится раньше, чем это заметят. А если шлюз вернёт `500` — `@Transactional` откатит **перевод**, потому что не отправилась SMS.

> Перевод денег и отправка SMS разные по важности, но синхронный вызов делает их одинаково критичными. Слабое звено определяет надёжность всей цепочки.

### Почему `@Async` — не решение, а `dispatch()` — решение

```
Spring @Async       → задача в ThreadPoolExecutor, В ПАМЯТИ ПРОЦЕССА
                      SIGTERM / OOM → задача исчезла, следа нет нигде
Laravel dispatch()  → задача записана в Redis/Postgres, ВНЕ ПРОЦЕССА
                      процесс умер → воркер поднялся → задача на месте
```

Laravel давал **durability** по умолчанию, и заметить это было невозможно, потому что сделать неправильно там нельзя. В Java аналога «из коробки» нет — брокер достаётся руками и потому виден. Общее различие стеков: **PHP/Laravel прячет инфраструктуру за абстракцией фреймворка, Java выставляет её наружу.**

### Laravel queue — это брокер, просто без терминов

| Laravel | Термин |
|---|---|
| `dispatch()` | producer |
| таблица `jobs` / Redis list / SQS | **broker** |
| `php artisan queue:work` | consumer (отдельный процесс) |
| `$tries`, `$backoff` | retry policy |
| таблица `failed_jobs` | **DLQ** |
| `reserved_at` + `retry_after` | **visibility timeout → at-least-once** |
| `ShouldBeUnique` | идемпотентность (кривая, но попытка) |
| Horizon | мониторинг consumer lag |

Драйвер `database` — буквально «наивный фикс №2» из плана: таблица `jobs`, воркер забирает строки через `SELECT ... FOR UPDATE SKIP LOCKED`, колонки `attempts`, `reserved_at`, `available_at`. То есть outbox-паттерн я писал, не зная названия.

### Баг из Laravel, который оказался dual write problem

```php
DB::transaction(function () {
    $transfer = Transfer::create([...]);
    SendSmsJob::dispatch($transfer);   // job в Redis МГНОВЕННО, до COMMIT
});
// воркер подхватил через 2 мс → Transfer::find($id) → null → ModelNotFoundException
```

Тот самый «воспроизводится через раз и только на проде, где Redis быстрый». Лечится `->afterCommit()` / `'after_commit' => true`.

Но это **костыль над dual write**: Laravel держит job в памяти до коммита и отправляет после. Если процесс умрёт между `COMMIT` и отправкой в Redis — job потерян навсегда. Окно сузилось со 100 мс до 1 мс, но не закрылось. Настоящий outbox (`INSERT` в ту же транзакцию) этой дыры не имеет вообще — вот почему в финтехе спрашивают про outbox, а не про `afterCommit`.

### Task queue ≠ event log. Для SMS Kafka не нужна

```
TASK QUEUE (Laravel jobs, RabbitMQ, SQS)     EVENT LOG (Kafka)
  «СДЕЛАЙ вот это»                             «ВОТ ЭТО ПРОИЗОШЛО»
  один исполнитель                             N независимых читателей
  producer знает, что должно произойти         producer о читателях не знает
  сделал → удалил                              лежит N дней, можно перечитать
```

Честный вывод: для SMS правильный инструмент — task queue, Kafka была бы оверинжинирингом (ровно то, что MISSION запрещает). Kafka понадобится, когда:

```php
SendSmsJob::dispatch($transfer);
NotifyAntifraudJob::dispatch($transfer);
UpdateAnalyticsJob::dispatch($transfer);   // ← появился четвёртый → ПРАВИМ КОД ПЕРЕВОДА
```

Код денежной операции меняется из-за того, что аналитике что-то понадобилось. Плюс того, чего у джоб нет в принципе: **replay** (джоба выполнена и удалена), **межсервисность** (Laravel job — это PHP-класс, Java-сервис его не прочитает), **порядок и throughput**.

## Почему нельзя «просто пометить джобу как сломанную»

Мой вопрос по ходу: зачем пересылать сообщение, если можно, как в Laravel, пометить job как failed и перезапустить руками после фикса?

**Встречный вопрос: кто пометит? Мертвец не напишет себе эпитафию.**

```
A. Джоба бросила исключение   → воркер ЖИВ, поймал, знает что случилось
                                → failed_jobs, stacktrace. Ретраить бесполезно, нужен фикс.
B. Воркер перестал существовать → SIGKILL / OOM / питание
                                → никто ничего не поймал, писать некому
```

`failed_jobs` покрывает **только A**. Для B нужен другой механизм — и это `reserved_at` + `retry_after` (дефолт 90 с), то есть повторная выдача. Laravel всё это время присылал сообщения повторно, просто я не смотрел в `reserved_at`.

**Один механизм под четырьмя именами:** Laravel `retry_after` · SQS visibility timeout · RabbitMQ unacked-сообщение возвращается при разрыве соединения · Kafka heartbeat → rebalance → чтение с последнего закоммиченного offset'а.

### Почему выбор бинарный

Брокер отправил сообщение и не получил ack. Что случилось?

```
1. воркер умер сразу после получения
2. воркер умер после обработки, до ack
3. воркер жив, но 20 секунд в GC-паузе
4. воркер жив и ответил — ack утонул в сети
```

Снаружи все четыре **выглядят одинаково**. Тишина. Отличить мёртвого от медленного нельзя — это свойство любой системы с сетью, а не недоработка Kafka. Единственный сигнал — таймаут, а таймаут по определению угадывает.

| Считать мёртвым и переслать | Считать живым и ждать |
|---|---|
| Риск: обработали дважды | Риск: не обработали никогда |
| **at-least-once** | **at-most-once** |

Третьего нет. «Пометить как сломанную» — это скрытый at-most-once.

### Три состояния, а не два

```
SUCCESS         — знаем, что получилось
KNOWN FAILURE   — знаем, что не получилось     ← failed_jobs
UNKNOWN         — не знаем ничего              ← здесь вся боль
```

Прерывание — не провал, а отсутствие информации. Реакция разная: на known failure — разбор и фикс, на unknown — тихо переделать. Практически: сервер перезагрузили, 5000 джоб были in-flight — они не сломались, их прервали, будить дежурного не за чем.

### Ловушка: дубликаты без единого падения

```php
'retry_after' => 90,   // config/queue.php
--timeout=120          // queue:work
```
```
t=0    worker-1 забрал джобу (работает 100 с)
t=90   retry_after истёк → worker-2 забирает ТУ ЖЕ джобу; worker-1 ЖИВ и работает
t=100  оба доделали → SMS ушла дважды
```

Правило: `retry_after` строго больше `--timeout`. Дубликаты здесь гарантированы конфигом, при полностью исправной системе.

## Kafka: партиция, offset, и чем лог отличается от очереди

**Партиция — это один физический append-only файл на диске конкретного брокера.** Топик — логическое имя над набором таких файлов; сущности «топик» на диске нет. Появляется из потолка: один файл = один диск = один писатель.

```
topic: transfer.completed (3 партиции)
  partition 0 → broker-1   offset: 0  1  2  3  4  5
  partition 1 → broker-2   offset: 0  1  2  3
  partition 2 → broker-3   offset: 0  1  2  3  4  5  6  7
```

**Offset — порядковый номер внутри своей партиции**, не внутри топика. `offset 3` в P0 и в P1 не связаны. Глобальной нумерации нет, потому что нет глобального файла → **порядок гарантирован только внутри партиции**. Партиция выбирается по `hash(key) % partition_count`; ключ `account_id` → события одного счёта всегда в одном файле и по порядку.

### Где живёт состояние — главное отличие

```
ОЧЕРЕДЬ (RabbitMQ, SQS, Laravel jobs) — состояние у БРОКЕРА
  [msg1][msg2][msg3] → выдал → получил ack → УДАЛИЛ → [msg2][msg3]
  брокер помнит про каждое сообщение: выдано? подтверждено? сколько попыток?

ЛОГ (Kafka) — состояние у ЧИТАТЕЛЯ
  [0][1][2][3][4][5][6][7]   ← файл неизменен, ничего не удаляется
           ▲ group-A: 3           ▲ group-B: 6
  брокер про сообщения не помнит НИЧЕГО. Он помнит числа.
```

Ответ на мой вопрос «очередь просто переходит на следующий месседж?» — **нет, ничего никуда не переходит**. Kafka-брокер не знает, обработано сообщение или нет. Он хранит файл и отдаёт по запросу «дай из партиции 0 начиная с позиции 43».

`commit offset` = дописать строку в служебный топик `__consumer_offsets`:
```
(group: "sms-service", topic: "transfer.completed", partition: 0) → 43
(group: "antifraud",   topic: "transfer.completed", partition: 0) → 7
```

Удаление — только по **retention** (`log.retention.hours`, дефолт 168 = 7 дней). Прочитали сто групп или ни одной — не влияет никак.

### Rebalance по шагам = тот же at-least-once

```
pod-1 закоммитил для P0 offset 42, фактически обработал до 47 (в памяти)
pod-1 умирает → heartbeat не пришёл → rebalance → P0 уезжает на pod-2
pod-2: «с чего начинать P0?» → __consumer_offsets: 42 → читает с 43
→ сообщения 43..47 обрабатываются ВТОРОЙ РАЗ
```

Никто ничего не «пересылал» — новый читатель открыл файл на позиции, записанной предыдущим, а тот не успел обновить закладку перед смертью. Ровно тот же механизм, что `reserved_at` в Laravel: **работа была сделана, но факт выполнения не зафиксирован, поэтому с точки зрения системы её не было.**

### Цена лога: head-of-line blocking

Партицию обрабатывает ровно один consumer в группе, строго по порядку. Offset — одно число, двигается только вперёд и подтверждает всё до себя, поэтому «отложить одно и взять следующее» нельзя.

```
RabbitMQ: кривое сообщение → nack → DLQ → остальные едут дальше
Kafka:    кривое сообщение на offset 43 → ПАРТИЦИЯ ВСТАЛА ЦЕЛИКОМ
```

**DLQ в Kafka — не функция брокера, а паттерн, который пишешь сам:** поймал исключение → сам положил в `...DLT` → закоммитил offset → поехал. В Spring Kafka это `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`.

### Изоляция групп: логически полная, физически нет

Отставание группы `analytics` на 2 часа группе `sms-service` не стоит ничего — нет ни одного общего изменяемого объекта. Но:

```
sms-service: читает хвост → он только что записан → page cache → sendfile (zero-copy) → быстро
analytics:   читает данные 2-часовой давности → в кэше их нет → холодное чтение с диска
             → ОС тянет старые сегменты в page cache → ВЫТЕСНЯЕТ горячий хвост
             → sms-service начинает попадать в диск
```

Формулировка: **логически группы изолированы полностью, физически делят железо брокера** (page cache, диск, сеть). Частично лечится tiered storage.

Опаснее в лаге другое — **обрыв о retention**:
```
retention 7 дней, analytics лежала 8 → её offset удалён вместе с сегментом → auto.offset.reset
   latest   → молча прыгает в конец, сутки событий потеряны навсегда
   earliest → молча считает всё заново
```
Оба варианта тихие: ошибки в логе нет, consumer «работает». Поэтому алерт ставят не на «отстал», а на «отстал настолько, что приближается к retention».

## Формулы для интервью

- **Exactly-once processing = at-least-once delivery + idempotent consumer.** Не «exactly-once delivery»: доставку никто не чинит, чинят эффект от повторной доставки. Цену платит потребитель, и платит идемпотентностью.
- **Redelivery — не недостаток брокера, который надо обойти, а единственный честный способ вести себя при неизвестном исходе.**
- **Брокер не делает систему надёжнее сам по себе — он меняет модель отказа:** вместо «упало сразу и видно» получаешь «примется когда-нибудь, а пока система несогласована». Для SMS хорошо, для «показать баланс после перевода» — нет.
- Вопрос, который в финтехе любят: **как гарантировать, что событие опубликовано тогда и только тогда, когда транзакция закоммичена** → transactional outbox.
