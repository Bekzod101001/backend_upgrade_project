## Разобрался

### Установка Kafka и что вообще такое starter/Testcontainers

Kafka — обычный Java-процесс, слушающий TCP. С версии KRaft (сейчас) ZooKeeper не нужен — брокер сам себе координатор, поэтому это один контейнер:

```yaml
kafka:
  image: apache/kafka:4.1.0
  environment:
    KAFKA_PROCESS_ROLES: broker,controller
    KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092   # адрес, который брокер СООБЩАЕТ клиенту
```

`KAFKA_ADVERTISED_LISTENERS` — самая частая причина «подключился, но не работает»: клиент коннектится к `bootstrap-servers`, брокер отвечает реальными адресами, и дальше клиент идёт по НИМ.

`spring-boot-starter-kafka` — три слоя: `kafka-clients` (Apache, сырой протокол) → `spring-kafka` (`KafkaTemplate`, `@KafkaListener`) → `starter` (автоконфигурация читает `spring.kafka.*` и сама создаёт бины). Без стартера пришлось бы руками писать `@Bean ProducerFactory/ConsumerFactory/KafkaTemplate`.

**Testcontainers** — поднимает настоящий `postgres:17`/`apache/kafka` из теста на случайном порту и гасит после. `@ServiceConnection` сам подставляет адрес в `spring.*` — конфига в тестах ноль. Побочный контейнер **Ryuk** — сторож, прибивающий забытые контейнеры при аварийном падении JVM.

**Apache** в названии — не связь с Apache HTTP Server, а принадлежность к Apache Software Foundation: нейтральный фонд, куда компании передают проекты (Kafka отдал LinkedIn в 2011). Название — в честь Франца Кафки, шутка Джея Крепса про «writing».

### Jackson 2 vs Jackson 3 — ловушка на весь день вперёд

Spring Boot 4 переехал на **Jackson 3** (`tools.jackson.*`), почти все статьи и Stack Overflow — про Jackson 2 (`com.fasterxml.jackson.*`). Конкретно сегодня:

- `JsonSerializer`/`JsonDeserializer` из spring-kafka — под Jackson 2, падают на `Instant` («add module jsr310»). Нужны `JacksonJsonSerializer`/`JacksonJsonDeserializer`.
- `ObjectMapper` для сериализации payload в outbox — тоже `tools.jackson.databind.ObjectMapper`, и `writeValueAsString` в Jackson 3 бросает `JacksonException`, который **RuntimeException**, а не checked — код проще, чем в Jackson 2.

Вывод про Boot 4: буду регулярно натыкаться на расхождения с туториалами, лечится не гуглом, а чтением, что реально лежит в JAR'е (`javap`, `unzip -l`).

### record vs class — не стиль, а разные гарантии

`record` — value object: все поля `final`, `equals`/`hashCode` по значению генерируются сами. Сработало незаметно в тесте:
```java
assertThat(bySms).isEqualTo(event);   // объект, ПЕРЕСОБРАННЫЙ из JSON на стороне consumer'а
```
прошло только потому, что `TransferCompletedEvent` — record. Будь он классом — тест бы не скомпилировался в вывод без ручного `equals`.

`Transfer`/`Account` не могут быть record: JPA нужен изменяемый setter (`setBalance`, dirty checking с Day 4), no-args конструктор и не-`final` класс для lazy-прокси — все три требования record проваливает.

Правило: **record — где важно значение** (DTO, события), **class — где есть identity/изменяемое состояние** (JPA-сущности).

### Структура пакетов: package by feature, не package by layer

Отверг классику `controller/service/repository/entity/dto` — группировка по техническому типу размазывает одну фичу по пяти папкам. Отдельно отверг `model/`: там оказались бы сущности с **несовместимыми правилами изменения** (JPA-entity меняется миграцией, HTTP-DTO — версией API, Kafka-контракт — ломает чужие сервисы), и такая папка подталкивает возвращать `Transfer` прямо из контроллера.

`exception/` — согласился делать сразу, а не после «накопится 5-8»: раз это имитация прода, траектория предсказуема (уже видно 8-10 исключений на пару недель вперёд из TODO), а цена завести папку — тридцать секунд.

Итог:
```
transfer/
  event/       TransferCompletedEvent — публичный контракт модуля
  exception/   InsufficientBalanceException, IdempotencyKeyConflictException
  (корень)     Transfer, TransferRepository, TransferService, TransferExecutor,
               TransferEventPublisher, TransferController, TransferRequest
kafka/         KafkaTopics — единственный владелец имён топиков
notification/  TransferNotificationListener — ноль импортов из transfer.*
outbox/        общий, не привязан к transfer — по природе паттерна (см. ниже)
```

### Вариант A → фантомное событие

```java
@Transactional
void execute(...) {
    ...
    eventPublisher.publish(event);   // ДО commit
}   // UPDATE балансов — при flush, то есть ПОСЛЕ publish()
```
Тест `TransferDualWriteTest` (вариант A): триггер роняет `UPDATE accounts` на commit — Postgres откатывает всё, Kafka откатить не может. Консьюмер получает событие о переводе, которого не существует ни в одной таблице. Postgres и Kafka — независимые системы, атомарного коммита между ними нет.

### Вариант B → тихая потеря (и баг, который поймал сам пользователь)

Публикация после `commit()`. Фантом ушёл, но в первой версии кода провал `publish()` **ронял ответ клиенту** — процитировал же правило «нельзя ронять успешную операцию из-за побочного эффекта» и тут же его нарушил. Поймано вопросом: «какого хуя клиент получил ошибку, это же просто publish, у клиента перевод уже сработал».

Починил: `publish()` обёрнут в try/catch, провал только логируется. Но отсюда прямое следствие — **потеря становится тихой**: клиент видит успех, ретрая не будет, единственный след — `log.error`, а при SIGTERM/OOM не будет и его. `TransferEventLossTest` (позже удалён, заменён на `OutboxRelayRecoveryTest`) воспроизвёл это до фикса.

Правило, которое вывели вдвоём: **после коммита операция успешна, ничего дальше не имеет права превратить её в ошибку** — но именно поэтому провал побочного эффекта обязан теряться молча, а не громко.

### Доказательство: `kafkaTemplate.send()` асинхронен, хотя не выглядит так

`KafkaSendIsAsyncTest`: `send()` возвращает `CompletableFuture` за ~850 мкс, `future.isDone() == false`, подтверждение прилетает в потоке `kafka-producer-network-thread`, не в вызывающем. Отсюда и тихая потеря в варианте B: при лежащем (но уже «прогретом», с закэшированными метаданными) брокере `send()` не бросает исключение сразу — кладёт в буфер, фоновый поток ретраит `delivery.timeout.ms` (2 мин по умолчанию) и только потом отдаёт ошибку в `Future`, который никто не слушает.

### Transactional outbox — реализация

```
V3__create_outbox.sql   id, topic, partition_key, payload jsonb, created_at, processed_at (null = не отправлено)
OutboxEvent              entity, @JdbcTypeCode(SqlTypes.JSON) — Hibernate 7 хранит JSON без доп. библиотек
OutboxEventRepository    findBatchForPublishing: FOR UPDATE SKIP LOCKED
                          (jakarta.persistence.lock.timeout = -2 — константа SKIP_LOCKED)
OutboxPublisher           интерфейс — граница между релеем и способом доставки
KafkaOutboxPublisher      реализация, голый StringSerializer (payload уже JSON-текст)
OutboxRelay               @Scheduled(fixedDelay = 1000) + @Transactional, Laravel queue:work на Postgres
```

`TransferExecutor.execute()` пишет `OutboxEvent` в ТУ ЖЕ транзакцию, что и `UPDATE accounts` — INSERT либо коммитится, либо откатывается вместе с деньгами. `TransferService` больше не содержит ни одного упоминания Kafka.

Аналогия, подтверждённая в разговоре: outbox механически = драйвер `database` у Laravel-очередей (`SELECT ... FOR UPDATE SKIP LOCKED`, `reserved_at`/`processed_at`). Разница ровно там, где была дыра: Laravel job кладётся в очередь в момент `dispatch()`, **до** гарантии, что бизнес-транзакция удалась (отсюда костыль `afterCommit`); outbox-строка пишется **в той же** транзакции — атомарность не дисциплина программиста, а гарантия самой БД.

### Технические ловушки при написании OutboxRelay (все три стоит запомнить — не банальность)

1. **`@ConditionalOnMissingBean(KafkaTemplate.class)` проверяет сырой тип, дженерики стёрты.** Второй `@Bean KafkaTemplate<String,String>` заставил Boot решить «KafkaTemplate уже есть» и вообще не создать стандартный `KafkaTemplate<String,Object>`, нужный `TransferEventPublisher`. Починил своим интерфейсом `OutboxPublisher` — не обход бага, а правильная архитектурная граница (релей не должен знать про `KafkaTemplate` вообще).
2. **`KafkaProperties.buildProducerProperties()` не видит адрес Testcontainers.** `@ServiceConnection` подменяет bootstrap-servers через отдельный бин `KafkaConnectionDetails`, который учитывает только автоконфигурация. Собирать конфиг вручную из `KafkaProperties` — получить нерабочий `localhost:9092`. Починил — беру готовый `ProducerFactory<Object,Object>.getConfigurationProperties()`.
3. **`JacksonJsonDeserializer` требует заголовок `__TypeId__`**, который пишет только `JacksonJsonSerializer`. Голый `StringSerializer` в релее его не добавляет. Починил `spring.json.value.default.type` в конфиге консьюмера — работает, пока в топике один тип события; со вторым понадобится `spring.json.type.mapping`.

### Логи провалившихся операций — это уже observability, отдельный слой

Спросил: outbox классно чинит доставку, но куда пишутся логи провалившихся публикаций?

Сейчас — буквально в stdout через SLF4J/Logback (`log.error` в `OutboxRelay`), и это правильно назвать другим слоем задачи:

```
OUTBOX/RELAY решает:   "событие переживёт краш и будет отправлено"
OBSERVABILITY решает:  "человек узнает, что краш вообще был"
```

Независимые задачи: можно иметь идеальный outbox без единого алерта (узнаешь о проблеме от клиента в поддержке) и наоборот — прекрасный мониторинг без durability (узнаешь мгновенно, но событие всё равно потеряно).

`spring-boot-starter-actuator` в проекте уже есть, просто не подключён к делу. Настоящее решение — Micrometer-метрика (`outbox.publish.failures`, лейбл по топику) → `/actuator/prometheus` → Prometheus scrape → Grafana → alertmanager. Плюс метрика `SELECT count(*) FROM outbox WHERE processed_at IS NULL` — тот же смысл, что consumer lag у Kafka: не «есть необработанные», а «сколько их и растёт ли». Не сделано сегодня, зафиксировано как будущая тема — TODO.

### Один outbox на все события, а не по одному на тип

Спросил: outbox общий на все ивенты — не засорится ли? И почему нет готового решения из коробки, раз паттерн одинаковый?

**Один общий — это норма, не самодеятельность.** У Debezium есть готовый **Outbox Event Router** (Single Message Transform), спроектированный именно под форму таблицы, до которой мы дошли сами: `id, aggregate_type, aggregate_id, type, payload`. `OutboxRelay` делает `SELECT ... SKIP LOCKED ORDER BY id LIMIT N` по всей таблице сразу, независимо от типа события, и публикует каждую строку в её собственный `topic` — ему всё равно, что лежит в `payload`, он его не парсит.

**Засорение — реальная проблема, но не там, где кажется.** Конкуренция при чтении не страдает: частичный индекс `WHERE processed_at IS NULL` держит запрос дешёвым, сколько бы обработанных строк ни скопилось рядом. Проблема в другом — строки **не удаляются**, `processed_at` это пометка, а не `DELETE`. При стабильной нагрузке таблица растёт без границ. Тот же нерешённый вопрос, что dedup window для idempotency-ключей на Day 5 — паттерн не говорит, сколько хранить и как чистить, это отдельное архитектурное решение (retention/cleanup job, уже в TODO).

**Почему нет `@EnableOutbox` из коробки Spring.** Паттерн универсален только на уровне идеи («durable write рядом с бизнес-данными → relay → broker»), а не в деталях: какая БД (у каждой свой WAL/CDC), какой брокер, формат сериализации, ключ партиционирования, retention policy, polling vs CDC — всё это специфично для системы. Ровно тот же разговор, что был про идемпотентность на Day 5: концепция универсальна, а «что считать одинаковой операцией/событием» — бизнес-специфично, поэтому готовой библиотеки нет и не будет.

Готовые решения существуют, но не «из коробки Boot», а отдельным выбором со своей ценой:

| Инструмент | Что даёт | Чем платишь |
|---|---|---|
| **Debezium** | читает WAL Postgres напрямую, без polling, задержка ~мс | нужен Kafka Connect — ещё один инфраструктурный компонент, DBA должен включить `wal_level=logical` |
| **Eventuate Tram** (JVM) | готовая библиотека transactional outbox + saga | завязка на их фреймворк, своя модель транзакций |
| Managed (AWS DynamoDB Streams) | outbox встроен в саму БД | применимо только если СУБД — DynamoDB |

Наш `@Scheduled`-polling — самый простой вариант этого спектра: без новой инфраструктуры, задержка до 1 секунды, достаточно для SMS/антифрода. Debezium — следующий логичный шаг, если секунда задержки когда-нибудь станет проблемой.
