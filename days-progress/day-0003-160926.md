## Разобрался

- **Lost update (повторение, подробный разбор в [Day 2](day-0002-150926.md)):** две транзакции читают одно значение, каждая считает новое в приложении по своему чтению, и последняя запись затирает предыдущую. Ошибок нет, обе транзакции «успешны».
  - Модель: двое скачали один Excel, каждый дописал строчку и загрузил обратно. На сервере остался файл последнего, правка первого пропала.
  - В MiniBank: `TransferConcurrencyTest` до lock'ов — 10 транзакций прочитали Alice = 1 000 000, каждая записала `SET balance = 80000000`, прошли все 10 переводов вместо 5.
  - Признаки: паттерн read → посчитал в Java → write; в `UPDATE` уходит готовое число, посчитанное по устаревшему чтению; баг тихий и всплывает только на сверке.
  - `@Transactional` не спасает: атомарность есть, но на `READ COMMITTED` две транзакции спокойно читают одно и то же значение.
  - Лечение: pessimistic lock (`@Lock(PESSIMISTIC_WRITE)`, так сейчас сделано в `AccountRepository.findByIdForUpdate`), атомарный `UPDATE ... SET balance = balance - ?`, optimistic lock `@Version`.
  - **Lost update vs deadlock:**

    | | Lost update | Deadlock |
    |---|---|---|
    | Что ломается | корректность: деньги посчитаны неправильно | доступность: законные операции падают |
    | Ошибки | нет, всё «успешно» | `deadlock detected` → `CannotAcquireLockException` |
    | В MiniBank | до lock'ов | после lock'ов на двух счетах, на встречных переводах |

    Deadlock — цена, которую заплатил за лечение lost update lock'ами.
- **Какие чтения лочить:** каждое, по которому потом записываешь значение, посчитанное в Java. У Bob тоже read → `+ amount` в Java → write, поэтому lock нужен и ему.
  - Ловушка: в `TransferConcurrencyTest` все переводы идут с Alice, поэтому lock только на Alice случайно выстроит в очередь и Bob'а, и тест может позеленеть. Стоит добавить поток, который переводит Bob'у с другого счёта, и lost update на Bob вернётся. Зелёный тест ещё не доказательство.
- **Блокировать обе строки создаёт новый риск:** встречные переводы A→B и B→A одновременно (Tx1 держит Alice и ждёт Bob, Tx2 держит Bob и ждёт Alice) дают deadlock. Текущий тест это не ловит.
- **`LockModeType`** — enum из JPA (`jakarta.persistence`), не из Hibernate. Описывает, *какой* lock нужен, а Hibernate dialect переводит его в SQL конкретной базы: Postgres/MySQL/Oracle пишут `FOR UPDATE`, SQL Server — `WITH (UPDLOCK, ROWLOCK)`.

  | Значение | Postgres | Смысл |
  |---|---|---|
  | `PESSIMISTIC_WRITE` | `for update` | эксклюзивный lock «буду менять», остальные ждут. **Нужен для перевода** |
  | `PESSIMISTIC_READ` | `for share` | разделяемый lock «не меняйте, пока читаю», могут держать несколько транзакций |
  | `PESSIMISTIC_FORCE_INCREMENT` | `for update` + `version++` | lock плюс принудительное увеличение `@Version` |
  | `OPTIMISTIC` | — | без lock'а, при commit проверка `@Version` → `OptimisticLockException` |
  | `OPTIMISTIC_FORCE_INCREMENT` | — | то же плюс `version++`, даже если entity не менялась |
  | `NONE` | — | по умолчанию, без блокировок |

  - `READ` и `WRITE` — старые синонимы `OPTIMISTIC` и `OPTIMISTIC_FORCE_INCREMENT` из JPA 1.0.
  - Optimistic-режимы работают только с полем `@Version`, у `Account` его пока нет.
  - Кроме `@Lock` в репозитории: `entityManager.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE)` и `entityManager.lock(entity, mode)`.
- **Почему для перевода не подходит `PESSIMISTIC_READ`:** две транзакции берут `for share` на Alice (shared lock'и совместимы), потом обе делают UPDATE, и каждая ждёт, пока другая отпустит свой shared lock. Получается deadlock. Для read → modify нужен `PESSIMISTIC_WRITE`, чтобы вторая транзакция ждала уже на чтении.
- **Когда нужен `PESSIMISTIC_READ` (`for share`):** когда читаешь строку, чтобы на её основании записать **что-то другое**, а саму строку не меняешь. Пока транзакция не закончилась, строку нельзя изменить, но другие читатели с таким же lock'ом не блокируются.
  - Пример из MiniBank: перевод проверяет, что счёт `ACTIVE`, и вставляет запись в историю операций. Параллельно кто-то замораживает счёт. `for share` на счёте: переводы по нему идут параллельно, а `UPDATE status = 'FROZEN'` ждёт их commit.
  - Другие примеры: курс валют или тариф, который не должен поменяться посреди расчёта; родительская строка при вставке дочерней. Для FK Postgres сам берёт аналогичный lock (`FOR KEY SHARE`) на родительской строке.
  - Антипаттерн: взять `for share`, а потом **менять эту же строку** приводит к deadlock (см. выше). Если собираешься менять, сразу бери `PESSIMISTIC_WRITE`.
  - На практике встречается редко: чаще либо сразу `PESSIMISTIC_WRITE`, либо более строгий уровень изоляции.
- **Laravel ↔ Spring:**

  | Что | Spring / JPA | Laravel |
  |---|---|---|
  | Транзакция | `@Transactional` | `DB::transaction(fn)` |
  | Pessimistic lock | `@Lock(PESSIMISTIC_WRITE)` | `->lockForUpdate()` |
  | Shared lock | `@Lock(PESSIMISTIC_READ)` | `->sharedLock()` |
  | Атомарный UPDATE | `@Modifying @Query("update ... set balance = balance - :amount ...")` | `->decrement('balance', $amount)` (возвращает число строк) |
  | Optimistic lock | `@Version` из коробки | руками: `where('version', $v)->update([..., 'version' => $v + 1])` |
  | Retry при deadlock | Spring Retry или руками | `DB::transaction(fn, attempts: 5)` |

  - Ловушка Laravel: `$model->balance -= 100; $model->save()` отправляет готовое число, это lost update. `$model->decrement('balance', 100)` атомарен.
  - В Laravel обычно MySQL (InnoDB) с `REPEATABLE READ` по умолчанию, в Postgres — `READ COMMITTED`. Детали блокировок отличаются, ответы про Postgres не переносить на MySQL один в один.
- **На интервью:**
  - *«Что такое lost update и как его избежать?»* Две транзакции читают одно значение, вычисляют новое в приложении, последняя запись затирает предыдущую. Лечится pessimistic lock'ом, атомарным UPDATE или optimistic locking через версию.
  - *«Какие режимы блокировок есть в JPA?»* Pessimistic (реальный lock в БД) и optimistic (проверка `@Version`).
  - *«`PESSIMISTIC_READ` vs `PESSIMISTIC_WRITE`?»* `for share` (разделяемый) против `for update` (эксклюзивный). READ — когда читаешь, чтобы записать что-то другое. WRITE — когда меняешь эту же строку.
  - *«`OPTIMISTIC` без `@Version`?»* Не работает.
