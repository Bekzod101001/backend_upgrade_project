## Разобрался

- **Что такое deadlock:** две и более транзакции ждут друг друга по кругу. Tx1 держит Alice и ждёт Bob, Tx2 держит Bob и ждёт Alice. Отличается от обычного ожидания lock'а тем, что ожидание замкнуто и само не закончится.
  - Модель: двое едят, на столе одна ложка и одна вилка, есть нужно обоими приборами.
  - Условия Коффмана: mutual exclusion, hold and wait, no preemption, circular wait. Чтобы deadlock стал невозможен, достаточно сломать любое одно, решения строятся на этом.
- **Что делает Postgres:** ждёт `deadlock_timeout` (по умолчанию 1 с), ищет цикл в графе ожиданий, **убивает одну транзакцию** (SQLSTATE `40P01`, `ERROR: deadlock detected`), остальные продолжают. Java-аналог на `synchronized` висел бы вечно: JVM deadlock не детектит.
- **Почему при этом в Java прилетает исключение** (мой вопрос): Postgres не разрешает deadlock за приложение, он только снимает жертву и откатывает её. Повторить транзакцию база не может: логика между запросами (проверка баланса, расчёт) живёт в Java, часть результатов уже отдана приложению, а внутри транзакции могли быть внешние эффекты. Молчать нельзя, иначе пользователь увидел бы «перевод успешен» там, где перевода не было. Аналогия: регулировщик разворачивает одну машину с моста, но не везёт её сам.
  - Spring переводит `40P01` в **`CannotAcquireLockException`** (наследник `PessimisticLockingFailureException`). Подтвердилось в тесте.
  - Варианты в приложении: не допускать (порядок lock'ов), retry всей транзакции, отдать клиенту ошибку с «повторите». В Laravel retry встроен: `DB::transaction(fn, attempts: 5)`.
- **Почему помогает порядок по `id`** (сначала не понял): `id` мы не меняем, меняется только порядок вызовов `findByIdForUpdate`. Транзакции ничего не знают друг о друге, у них разные `from`/`to`, но **одинаковый набор счетов** `{1, 2}`. Сортировка превращает разные входные данные в один и тот же порядок.
  - Кто держит счёт 1, гарантированно получит счёт 2: никто не может держать 2 и ждать 1. Круг не замыкается, ждущая транзакция ничего не держит.
  - «По возрастанию» не магия: по убыванию работало бы так же. `id` удобен тем, что уникален, известен до lock'а и легко сравнивается.
  - Бытовая модель: правило «сначала всегда паспорт, потом ключи» вместо того, чтобы каждый брал что хочет первым.
- **Deadlock ломает доступность, а не корректность:** деньги целы (18 транзакций откатились), но законные переводы падают ошибкой. Lost update наоборот: ошибок нет, а деньги посчитаны неправильно.
- **Почему упало 18 из 20, а не пара:** 20 транзакций лочат два счёта вперемешку, циклы образуются между многими парами сразу; Postgres убивает по одной из каждого цикла, оставшиеся образуют новые.
- **`for no key update`:** Hibernate 7 для Postgres генерирует на `PESSIMISTIC_WRITE` не `for update`, а `for no key update`. Он так же блокирует другие `UPDATE` и lock'и на строке (lost update исключён), но не блокирует `FOR KEY SHARE`, который Postgres берёт при вставке строки с FK на этот счёт. Логика: мы меняем `balance`, но не `id`.
- **Ловушки Java, которые всплыли:**
  - сравнивать `Long` через `==` нельзя: кэш только −128..127, на тестовых `id` работает, на боевых ломается. Только `.equals()`;
  - `fromId == toId` залочит одну строку дважды (Postgres переживёт, lock уже свой), но перевод самому себе всё равно надо запретить валидацией.
- **Trade-offs фикса:** порядок lock'ов бесплатен и надёжен, но его должны соблюдать **все** места, которые лочат несколько счетов (будущие `refund`, `batchPayout`). Одно забытое место возвращает deadlock, поэтому в production обычно делают и порядок, и retry. Retry безопасен только если внутри транзакции нет внешних эффектов (SMS, HTTP).
- **На интервью:**
  - *«Что такое deadlock и что делает база?»* Круговое ожидание, база находит цикл и убивает одну транзакцию.
  - *«Почему база не повторяет транзакцию сама?»* Логика между запросами живёт в приложении.
  - *«Как избежать deadlock при переводах?»* Единый порядок захвата (по `id`) плюс retry на `40P01`.
  - *«Deadlock vs lock wait?»* Круговое ожидание против линейного.

## Теория и практика deadlock через ChatGPT

Отдельная тренировка: разбирал конкурентные транзакции, pessimistic locking и deadlock'и на задачках в ChatGPT.

### С чего начал

Базовый кейс перевода:

```java
@Transactional
public void transfer(Long fromId, Long toId, Long amount) {
    Account from = accountRepository.findByIdForUpdate(fromId).orElseThrow();
    Account to = accountRepository.findByIdForUpdate(toId).orElseThrow();
    from.setBalance(from.getBalance() - amount);
    to.setBalance(to.getBalance() + amount);
}
```

`findByIdForUpdate()` использует `@Lock(LockModeType.PESSIMISTIC_WRITE)`, что на уровне БД соответствует идее `SELECT ... FOR UPDATE`.

Важный момент: lock удерживается **не до завершения SELECT, а до конца транзакции** (`COMMIT` / `ROLLBACK`).

### Что такое deadlock

```
T1: transfer(10, 20)
T2: transfer(20, 10)

T1: lock Account(10) ✓
T2: lock Account(20) ✓
T1: хочет Account(20) → WAIT T2
T2: хочет Account(10) → WAIT T1
```

Главная ментальная модель:

- **WAIT** — я жду другую транзакцию, но она способна закончить и освободить ресурс.
- **DEADLOCK** — я жду транзакцию, которая прямо или косвенно сама ждёт меня.

`T1 → T2 → T3` — не deadlock, если T3 может продолжить работу. `T1 → T2 → T3 → T1` — уже deadlock.

### Как убрали deadlock в transfer

Проблема была в разном порядке захвата аккаунтов: `transfer(10, 20)` берёт 10 → 20, а `transfer(20, 10)` берёт 20 → 10.

Решение — **canonical lock ordering**:

```java
Long firstId = Math.min(fromId, toId);
Long secondId = Math.max(fromId, toId);
Account first = accountRepository.findByIdForUpdate(firstId).orElseThrow();
Account second = accountRepository.findByIdForUpdate(secondId).orElseThrow();
```

Теперь оба перевода захватывают 10 → 20. Если T1 уже взял 10, T2 зависнет на попытке взять 10 и даже не дойдёт до попытки взять 20. Поэтому T1 спокойно получает 20, заканчивает транзакцию и освобождает locks.

**Ключевой вывод:** сортировка `id` важна не сама по себе. Важно, чтобы конкурирующие транзакции захватывали ресурсы в одинаковом порядке. Можно было использовать и DESC, главное — соблюдать правило везде.

### Задачи, которые разобрал

1. **Независимые ресурсы.** `T1: transfer(10, 20)`, `T2: transfer(30, 40)` — общих ресурсов нет, транзакции друг другу не мешают.
2. **Обычное ожидание.** T1 держит 10 и хочет 20 → WAIT; T2 держит 20, хочет 30, получает его и коммитит. После COMMIT T2 освобождается 20, и T1 продолжает. Не deadlock: `T1 → T2`, но T2 никого не ждёт.
3. **Классический deadlock.** T1 держит 10 и хочет 20, T2 держит 20 и хочет 10.
4. **Цепочка из трёх транзакций.** `T1 → T2 → T3`, где T3 может работать: deadlock отсутствует, T3 заканчивает → продолжает T2 → затем T1. Искать нужно именно **цикл**, а не большое количество WAIT.
5. **Deadlock между разными типами ресурсов.**
   ```
   T1: lock Account, затем lock User
   T2: lock User, затем lock Account

   T1: lock Account(10) ✓
   T2: lock User(5) ✓
   T1: хочет User(5) → WAIT
   T2: хочет Account(10) → WAIT
   ```
   Одного правила `ORDER BY id` недостаточно: нужен согласованный **порядок типов ресурсов** (например, User → Account), и все транзакции должны его соблюдать.
6. **Deadlock в purchase/remove flow.**
   ```
   buy():            lock Buyer → lock Product → lock Seller
   removeFromSale(): lock Seller → lock Product

   T1: lock Buyer(10) ✓
   T2: lock Seller(20) ✓
   T1: lock Product(500) ✓
   T2: хочет Product(500) → WAIT T1
   T1: хочет Seller(20) → WAIT T2
   ```
   Исправление — согласовать порядок захвата, например Product → User. Если пользователей несколько, внутри типа тоже нужен стабильный порядок: `Product(500)`, `User(minId)`, `User(maxId)`.

### Дополнительные выводы

- Java-код внутри одной транзакции выполняется сверху вниз, но несколько транзакций выполняются конкурентно, поэтому возможны чередования вида `T1 SQL #1 → T2 SQL #1 → T1 SQL #2 → ...`.
- Если транзакция зависла на `findByIdForUpdate(...)`, следующая строка Java-кода этой транзакции пока не выполняется.
- JPA dirty checking: если entity загружена внутри `@Transactional` и остаётся managed, отдельный `repository.save(entity)` после изменения полей обычно не нужен — Hibernate сформирует UPDATE при flush/commit.

### Алгоритм анализа deadlock

1. Определить, какие ресурсы блокирует каждая транзакция.
2. Выписать порядок захвата locks.
3. Посмотреть, какие транзакции могут выполняться одновременно.
4. Построить зависимости вида `T1 waits for T2`.
5. Искать цикл ожиданий.
6. Для предотвращения использовать единый порядок захвата ресурсов:
   - единый порядок типов (например, Product → User → Account);
   - единый порядок ресурсов одного типа (`id ASC`).

Коротко: **deadlock = циклическое ожидание, canonical lock ordering ломает возможность образования цикла.**
