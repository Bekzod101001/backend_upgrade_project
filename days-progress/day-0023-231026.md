# Day 23 — 2026-10-23

Задача с работы: RFC по переносу списка товаров кабинета продавца (`getProducts`) из монолита (ke-backend) в сервис ассортимента. Артефакт — реальный RFC, без копирования конфиденциального кода, только архитектура и решение.

## Backend story: перенос getProducts из монолита в ассортимент

### PROBLEM

Экран списка товаров кабинета продавца вызывает ручку монолита `GET /seller/shop/{shopId}/product/getProducts` — это не одна операция, а сборщик: SQL по `product/sku/image`, несколько SKU-выборок, несколько энричеров (часть — по HTTP к внешним сервисам), пара походов в PIM. Пока ручка живёт в монолите, кабинет продавца физически не отделить от него. Нагрузка заметная: сотни тысяч вызовов в сутки, пик — около 10 rps, p95 — пара секунд. Отдельная смежная проблема: счётчики вкладок считаются другим кодом монолита и на проде уже расходились с реальным списком на десятки тысяч товаров.

### CONTEXT

Blast radius — high: это главный экран кабинета продавца. До этого уже была волна изменений, которая переключила шаг SQL на кеш ассортимента внутри самого монолита — ускорило ручку, но вызов из кабинета так и остался в монолите. Есть смежные ручки (счётчики вкладок, внешний OpenAPI для продавцов с похожим списком), которые решают ту же задачу параллельно. Источник истины по товару — пока монолит, ассортимент держит зеркало через CDC (Change Data Capture) с задержкой в секундах.

### OPTIONS

1. **Ассортимент сам собирает весь ответ** (свои данные + проекции через Kafka-топики других доменов + прямые HTTP-вызовы к внешним сервисам). Плюс — один контракт, паритет проверяется прямым сравнением ответов старого и нового пути, фронту нужно поменять только адрес. Минус — ассортимент берёт на себя чужие домены, от чего команда раньше уже отказывалась.
2. **Сборка на фронте**: ассортимент отдаёт только свои данные, остальное фронт собирает сам отдельными вызовами. Минус — у части внешних сервисов просто нет нужной ручки под продавца, часть колонок останется пустой или всё равно на монолите.
3. **Отдельный BFF-сервис** только под этот список. Не размывает границы ассортимента, но это новый сервис — новый владелец и новое дежурство.
4. **Остаться на монолите** с уже сделанным кешем ассортимента. Быстро и ничего не ломает, но цель (оторвать кабинет от монолита) не достигается.

### DECISION

Выбран вариант 1: две новые ручки в ассортименте — список и статистика по товарам кабинета. Авторизация — токен продавца + проверка доступа к конкретному магазину. Контракт ответа не меняется, но параметры валидируются строже, чем в монолите (неизвестное значение → `400`, а не тихая подстановка дефолта). Чужие данные ассортимент получает так же, как их получает монолит, — подпиской на те же Kafka-топики в свои таблицы плюс прямые HTTP-вызовы к тем же внешним сервисам.

### IMPLEMENTATION

Раскатка построена как postgres-strangler, а не big-bang:

- задача 0 — согласование RFC и снятие baseline-метрик;
- ручки на тех полях, что уже есть в ассортименте;
- на фронте — флаг через GrowthBook, сначала теневой режим (вызываем оба пути, сравниваем ответы, не показываем новый пользователю);
- дальше — параллельные независимые интеграции по доменам (рейтинг, статистика товара, прогноз дефицита, рекомендованная цена, акции, внешние обогащения) — каждая со своим владельцем, задержка одной не блокирует остальные;
- контрактные тесты + тень на проде + нагрузочное тестирование;
- раскатка под флагом по процентам (тестовые магазины → 1% → 10% → 50% → 100%, не чаще одного шага в сутки);
- старый путь выключается только после 2–4 недель стабильности на 100%.

Режимы флага: `monolith` / `shadow` / `assortment_with_fallback` (автоматический откат на монолит при 5xx, таймауте, ошибке парсинга, после нескольких сбоев подряд) / `assortment`. Решение о пути фиксируется на пользователе на всю сессию пагинации, чтобы не прыгать между источниками внутри одной сессии просмотра списка.

### FAILURE MODES / RISKS

- **Организационный риск — главный**: без согласия владельца ассортимента на хранение проекций чужих данных план не стартует вообще — это уже поднималось раньше и решалось отказом.
- Проекция без начальной загрузки: у товаров, по которым давно не было событий, нужные поля будут пустыми → нужен разовый снэпшот при старте, а не только подписка на новые события.
- Бейджи/метки, которые ничем не очищаются ("висят вечно"), если источник перестал их обновлять → нужен TTL на очистку.
- Отставание CDC после записи — пользователь может не увидеть свежую правку сразу → компенсируется оптимистичным обновлением на фронте.
- Разная семантика поиска (точное совпадение в новой ручке vs полнотекстовый поиск в старой) — тихо меняет поведение для пользователя.
- Рассинхрон между списком и счётчиком — та же проблема, которая была причиной задачи, может воспроизвестись и на новом пути, если считать по разным источникам.
- Утечка чужих данных (например, причины блокировки товара с именем модератора) — нужна серверная проверка доступа, чувствительные поля не отдаются клиенту вообще.
- Деградация по полю, а не по всему ответу: если один энричер упал, остальной ответ всё равно должен собраться (так же, как уже устроено в монолите).
- Рост нагрузки на ассортимент и внешние сервисы от теневого режима — временно трафик кратно выше, это нужно явно учитывать в нагрузочном плане.
- Стоп-правила на раскатке: ошибки выше baseline, p95 выше порога дольше 15 минут, доля автооткатов выше порога дольше 10 минут, жалобы вида «товар пропал из списка».

### RESULT

Документ на стадии черновика — RFC ещё не согласован, задачи по плану не начаты. Результат пока не измерить, это фиксация решения и плана, а не отчёт о внедрении.

### WHAT I WOULD HIGHLIGHT FOR MYSELF

- Чёткий пример **strangler fig pattern**: не переписывать всё сразу, а переключать трафик постепенно под флагом, с автоматическим откатом и теневым сравнением до того, как пользователь увидит новый путь.
- Хороший пример, что миграция ручки — это не просто "перенести SQL в другой сервис": главная сложность и главный риск — в границах владения данными (кто должен держать чужие проекции) и в организационном согласии, а не в технике копирования запроса.
- Валидация "неизвестное значение → ошибка, а не тихий дефолт" — осознанное ужесточение контракта при миграции, а не случайная строгость.
- Явные стоп-правила раскатки (конкретные пороги и длительности) — то, что в учебных проектах обычно не проговаривается, а в проде обязательно.
