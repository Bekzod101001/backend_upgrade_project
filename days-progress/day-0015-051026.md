# Day 15 — 2026-10-05

Тема дня: **что такое harness в контексте ИИ** — разобрал всю инженерную обвязку вокруг "голой" LLM: function calling, сжатие контекста, оркестрацию субагентов и то, откуда у модели берётся способность раскладывать задачу на шаги (reasoning).

## Разобрался

### Harness — инженерный слой вокруг stateless-модели

Модель сама по себе — чистая функция `текст → текст`, без памяти между вызовами и без рук. Harness — это весь код вокруг неё, который превращает это в работающего агента:

- **Function calling / tool use** — конкретный протокол: harness передаёт модели JSON-схему доступных функций (имя + параметры), модель (обученная на это через RLHF) генерирует структурированный текст-вызов вместо обычного ответа, harness парсит его, валидирует, выполняет реальный side-effect (`Bash`, `Read` и т.п.) и вставляет результат обратно в контекст как новое сообщение. Ключевой момент: сам "вызов" — это не программный вызов функции, а обычная генерация текста в заранее условленном формате; вся "настоящая" работа (выполнение команды) — на стороне harness.
- **Каждый tool result запускает новый inference-вызов** — модель не "ждёт" между токенами, у неё нет состояния. Harness при каждом шаге цикла заново отправляет весь контекст (историю + system prompt + tool schemas + новый tool_result) как новый HTTP-запрос. Это stateless request-response, как REST API без сохранения состояния на сервере — вся история передаётся клиентом (harness) заново при каждом вызове.
- **Context management** — сжатие/суммаризация истории, когда накапливается слишком много токенов.
- **System prompt / configuration injection** — harness перед каждым запросом подмешивает в контекст свой собственный текст, который модель не писала: `CLAUDE.md`, system-reminder блоки, настройки пользователя. Это конфиг, который живёт в harness, а не в модели.
- **Retry-логика** — harness перезапрашивает шаг при сбое (невалидный tool call, rate limit, таймаут), без краха всего цикла.
- **Оркестрация субагентов** — harness умеет породить отдельную, независимую копию модели с чистым контекстом для подзадачи (инструмент `Agent`, параметр `subagent_type`), дождаться её финального ответа и вернуть его родительскому циклу как обычный tool_result. Оркестрация — это способность/механизм; субагент — конкретный экземпляр, который этим механизмом порождается (параллель: Kubernetes scheduler vs конкретный под).

### Reasoning — не отдельный "режим мышления", а тот же next-token-prediction

Reasoning — это промежуточные токены перед финальным ответом (chain-of-thought), которые модель использует как scratchpad, а не отдельная архитектура.

Откуда берётся сама способность раскладывать задачу на шаги — два источника, оба статистические, без явного алгоритма разбиения:

1. **Pretraining** — в тренировочном корпусе огромное количество текста, где люди естественно рассуждают поэтапно (математика, код, форумные объяснения). Модель выучивает статистическую форму: после сложной задачи с высокой вероятностью идёт пошаговый разбор, потому что так выглядел человеческий текст.
2. **RL / RLHF / RLVR** — модель генерирует рассуждение + ответ, если ответ проверяемо правильный (математика, код с тестами) — веса сдвигаются в сторону именно такого типа рассуждения. Повторяется миллионы раз → закрепляются паттерны разложения, которые эмпирически коррелируют с правильными ответами.

Важно: нет отдельного "модуля планирования" — decomposition — эмерджентное свойство из (1) и (2), а не встроенная фича архитектуры. Отсюда и реальный failure mode: на задачах, непохожих на тренировочные данные, модель может выдавать правдоподобно выглядящие, но не ведущие к правильному выводу шаги (unfaithful reasoning).
