## Разобрался

### SDD vs TDD vs code-first

- TDD — цикл **Red → Green → Refactor**: тест сначала красный (кода ещё нет), потом минимальный код до зелёного, потом рефакторинг без изменения поведения.
- SDD — спецификация (например OpenAPI) не просто документация "для галочки", а источник истины, из которого код **механически проверяется/генерируется**; отличие от "просто написали ТЗ" — спека остаётся живым, проверяемым артефактом, а не игнорируемым планом.
- Классический подход без процесса называется **code-first** (или **code-and-fix** / "cowboy coding" в более хаотичном варианте).
- **Почему SDD стал актуален именно с агентами:** агент, как и любая LLM, галлюцинирует архитектурные решения там, где нет явного контракта (next-token prediction додумывает правдоподобно, но не обязательно верно). Спека — это grounding для агента, тот же принцип, что в tool calling: сужает пространство возможных интерпретаций задачи.
- **Ключевая ловушка, которую поймал сам в разговоре:** если спеку тоже генерирует агент, это не убирает галлюцинацию, а просто переносит её на уровень выше — агент идеально честно реализует свою же неверную догадку. Решает это не "кто пишет спеку", а **обязательный шаг ревью человеком** именно спеки (компактный артефакт, дёшево вычитать), а не всего сгенерированного кода (дорого вычитывать построчно). Прямая параллель — `EnterPlanMode`/`ExitPlanMode` в Claude Code: план = спека, человек одобряет до того, как агент тронет файлы.

### LLM vs harness vs агент

- LLM — голый "промпт → текст", без памяти, без возможности что-либо сделать.
- Harness — зонтичный термин для любой инженерной обвязки вокруг LLM (память, файлы, tools, лимиты). Агентность — **не отдельный слой поверх harness**, а свойство, которое harness может иметь или не иметь: простой чат-harness без цикла — просто вызывает модель один раз на вопрос; агент — harness, который реализует tool calling + `while`-цикл принятия решений (модель сама решает: "ещё один шаг" или "хватит"), без участия человека на каждой итерации.
- **"Агентская модель"** (GPT-5.5, Sonnet 5 и т.п.) — это не значит, что модель сама что-то выполняет. Значит, что модель дообучена (RLHF) лучше решать, когда генерировать tool call вместо текста. Модель только генерирует structured tool call — реально выполняет (HTTP-запрос, чтение файла) harness, не модель.
- Прямое доказательство на собственном примере: `WebFetch`/`WebSearch` в system-reminder этого диалога — это tools harness'а (Claude Code), не часть модели (Sonnet 5). Без harness'а с этими tools модель не может "сходить" никуда, только сгенерировать текст (в т.ч. галлюцинированный).

### Payment-флоу — реализация

- Изучил существующие конвенции проекта на `Transfer`/`TransferExecutor`/`TransferService`/`OutboxEvent` перед тем как писать новый модуль — чтобы не плодить второй стиль архитектуры в одном проекте.
- Реализовано: `PaymentIntent` (entity, id — UUID, генерируется в конструкторе), `PaymentIntentRepository.findByIdForUpdate` (тот же `PESSIMISTIC_WRITE`-паттерн, что у `AccountRepository`), `ProviderClient`/`InMemoryProviderClient` (заглушка вместо реального HTTP, валидирует номер лицевого счёта), `PaymentService.createIntent` (шаг 1, сетевой вызов вне транзакции, save без явной `@Transactional`) и `PaymentService.confirmPayment` (шаг 2, явная `@Transactional`, row lock на intent + account, идемпотентный no-op на повторный confirm), outbox-событие в топик `payment.completed`, миграция `V4__create_payment_intents.sql`.
- Добавлен `PaymentServiceTest` (4 теста, по образцу `TransferServiceTest`, без сидеров): debit + статус COMPLETED, идемпотентность повторного confirm, отказ провайдера на невалидном номере счёта (до любой записи в БД), insufficient balance оставляет intent в статусе CREATED (retryable). Весь сьют проекта остался зелёным.
- **Важное наблюдение про тесты:** в проекте нет сидеров/фабрик в духе Laravel (`db:seed`, factories). Каждый тест (`TransferServiceTest` и др.) создаёт ровно те строки, которые ему нужны, напрямую через `accountRepository.save(new Account(...))` внутри самого теста — Testcontainers поднимает честный чистый Postgres с Flyway-миграциями, без предзаполненных данных. Это не "более серьёзный уровень" в смысле недоступности сидеров технически (в Java-экосистеме есть `@Sql`-скрипты, test data builders — аналоги существуют), а осознанный выбор: явные данные в каждом тесте читаются как часть самого теста (что именно проверяется), а не прячутся в общий фикстур-файл.

### SDD на практике — contract-first в MiniBank

- Посмотрел реальный прод-пример (`uzum/assortment`, Gradle multi-module): отдельный модуль `http-api-spec` содержит ТОЛЬКО OpenAPI YAML (`paths/`, `schemas/`), без единой строчки Java; `service`-модуль генерирует из него Java-интерфейсы контроллеров (`DictionaryControllerApi` и т.п.) и DTO через `openapi-generator`; реальный класс пишет `implements DictionaryControllerApi` и реализует только тела методов.
- Повторил ту же механику в MiniBank (один Maven-модуль, без выделения отдельного под-модуля под спеку — упрощение для текущего масштаба проекта): `src/main/resources/openapi/payments.yaml` → `openapi-generator-maven-plugin` в `pom.xml` (`generatorName=spring`, `interfaceOnly=true`, `useSpringBoot3=true`) → генерация в `target/generated-sources/openapi` интерфейса `PaymentsApi` и моделей `PaymentInitRequest`/`ConfirmPaymentRequest`/`PaymentIntentResponse` в пакет `uz.minibank.api`.
- `PaymentController implements PaymentsApi` — путь, HTTP-метод, типы полей заданы спекой, не контроллером; несовместимое изменение `payments.yaml` ломает компиляцию `PaymentController`, а не остаётся незамеченным до ревью.
- Ручные DTO-record'ы (`PaymentInitRequest`, `ConfirmPaymentRequest`, `PaymentIntentResponse`), написанные вручную в Day 18 до SDD-рефакторинга, удалены — заменены сгенерированными классами. `PaymentService` принимает/возвращает сгенерированные типы напрямую.
- Технические детали, не очевидные заранее:
  - Сгенерированный код тянет `com.fasterxml.jackson.annotation.*` (классический Jackson 2 namespace для модуля аннотаций) — завелось без конфликта с Jackson 3 (`tools.jackson.*`), который использует остальной проект: модуль `jackson-annotations` не переименовывался при переходе на Jackson 3, в отличие от `jackson-core`/`jackson-databind`.
  - Понадобились два дополнительных рантайм-зависимости, которые плагин сам в `pom.xml` не добавляет: `io.swagger.core.v3:swagger-annotations-jakarta` (аннотации `@Schema`/`@Operation` в сгенерированном коде) и `org.openapitools:jackson-databind-nullable` (тип `JsonNullable<T>` — отличает "поле отсутствало в JSON" от "поле было равно null").
  - Домейн-enum `PaymentStatus` и контрактный `PaymentIntentResponse.StatusEnum` держатся **сознательно раздельными** (не один и тот же enum на двух слоях) — домен не обязан меняться каждый раз, когда меняется контракт, и наоборот; сейчас мэппинг через `valueOf(name())`, явный, а не случайный, потому что имена совпадают.
