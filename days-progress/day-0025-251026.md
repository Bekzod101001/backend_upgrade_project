## Разобрался

### 1. Компиляция и выполнение кода

Компиляция — преобразование программы из одного представления в другое, не обязательно в машинный код напрямую.

**Java**: `.java` → (javac) → `.class` (байткод) → JVM → интерпретация/JIT → машинные инструкции. Байткод платформонезависим, JVM выполняет его на конкретной платформе. CPU не исполняет `.class` напрямую, потому что процессор понимает только инструкции своей архитектуры, а не байткод JVM.

**JavaScript/Vue**: Vue SFC + TypeScript → Vue Compiler/TS Transform → JavaScript → Vite/Rollup → браузер (V8) → интерпретация/JIT → машинный код. TypeScript обычно превращается в JS с удалением типов.

**PHP/Laravel**: HTTP Request → Nginx → PHP-FPM Worker → Zend Engine → PHP OpCodes → Zend VM. PHP компилируется в opcodes, которые выполняет Zend VM; OPcache кеширует opcodes, в PHP есть и опциональный JIT.

Вывод: деление языков на «компилируемые»/«интерпретируемые» сильно упрощает реальную картину — у всех трёх есть промежуточное представление и виртуальная машина.

### 2. JVM и JIT

JVM отвечает за загрузку классов, выполнение байткода, управление памятью, GC, потоки, JIT-компиляцию.

JIT (Just-In-Time Compilation) — компиляция кода в машинные инструкции во время работы приложения, на основе наблюдения за тем, какой код выполняется часто (hot code). Компилировать всё сразу не выгодно — компиляция тоже стоит времени/ресурсов, а JIT использует данные о реальном поведении программы для оптимизации.

Ключевые понятия: hot code, inlining (встраивание тела метода в место вызова), deoptimization (откат к менее оптимизированному выполнению, если предположения JIT перестали быть верными).

### 3. Жизненный цикл Java и PHP-FPM

Spring Boot — долгоживущий процесс: `java -jar` → JVM → Spring `ApplicationContext` → инициализация бинов → HTTP-сервер → обработка множества запросов. Объекты Spring могут жить между запросами.

PHP-FPM worker не умирает после каждого запроса, но обычное состояние PHP-запроса очищается между запросами; в классическом Laravel объекты приложения обычно создаются заново на каждый запрос. Исключение — Laravel Octane, где процессы долгоживущие и проблемы сохранения состояния между запросами могут возникать так же, как в Java.

Почему Java-приложение потребляет память в простое: heap/объекты, `ApplicationContext`, метаданные загруженных классов, JIT-скомпилированный код, стеки потоков, нативные структуры JVM, сетевые буферы. RAM ≠ CPU — память может быть занята при почти нулевой загрузке процессора.

### 4. Spring Singleton и потокобезопасность

`@Service`/`@Component` по умолчанию имеют scope singleton — один экземпляр бина на `ApplicationContext`. Несколько HTTP-запросов (потоков) могут одновременно работать с одним и тем же экземпляром. Если бин хранит изменяемое поле (например `currentUser`), это data race: один запрос может увидеть значение, записанное другим.

Правило: не хранить изменяемое состояние конкретного запроса в полях singleton-сервиса. Делать сервисы stateless — работать с аргументами метода, а не с полями объекта.

### 5. ThreadLocal

`ThreadLocal<T>` хранит отдельное значение для каждого потока. Опасность: HTTP-серверы используют пулы потоков, поток не уничтожается после запроса, а возвращается в пул — если значение не очищено, следующий запрос на том же потоке может получить устаревшие данные (утечка контекста между запросами).

Правильная очистка — `set` в начале, `remove()` в `finally`, чтобы очистка происходила и при обычном завершении, и при исключении. Вывод: ThreadLocal привязан к потоку, а не к HTTP-запросу.

### 6. Race Condition и Lost Update

`counter++` — не атомарная операция (READ → ADD 1 → WRITE). Два потока могут одновременно прочитать одно и то же значение, оба прибавить единицу и записать одинаковый результат — одно из увеличений теряется (Lost Update). Race condition — ситуация, когда корректность результата зависит от порядка выполнения конкурентных операций.

### 7. volatile

`volatile` обеспечивает видимость изменений поля между потоками и порядок операций (например, для флага `running` в цикле `while`). `volatile` НЕ делает составные операции атомарными — `volatile int counter` с `counter++` всё ещё подвержен lost update.

Сравнение: обычный `int` — нет гарантии видимости, нет атомарности; `volatile int` — видимость есть, атомарности нет; `synchronized` — видимость и атомарность при правильном использовании; `AtomicInteger` — и видимость, и атомарность. Запомнить: volatile — про видимость и порядок, а не про атомарность `++`.

### 8. AtomicInteger и CAS

`AtomicInteger.incrementAndGet()` атомарно увеличивает значение через атомарные механизмы процессора/JVM.

CAS (Compare-And-Swap) — изменить значение только если оно всё ещё равно ожидаемому; при неудаче (значение уже изменилось) операция сообщает о провале, и вызывающий код перечитывает значение и повторяет попытку (CAS loop). Современный `AtomicInteger` не обязан буквально использовать Java-цикл — может применяться специализированная атомарная инструкция процессора.

CAS vs synchronized: CAS не требует захвата монитора, при конфликте — повторные попытки, удобен для простых атомарных изменений; synchronized даёт взаимное исключение и позволяет защитить несколько связанных операций сразу, другие потоки ждут освобождения монитора. CAS не всегда быстрее — при высокой конкуренции повторные попытки могут быть дорогими.

### 9. Атомарность операции ≠ корректность бизнес-логики

Пример TOCTOU (Time of Check to Time of Use): `if (balance.get() >= amount) balance.addAndGet(-amount)` — каждая операция по отдельности атомарна, но проверка+списание вместе не атомарны. Два потока могут оба пройти проверку на основании одного и того же старого значения и уйти в минус.

Исправление — CAS loop: перечитывать текущее значение, проверять условие, пытаться `compareAndSet`, при неудаче повторить. Ограничение: работает для состояния внутри одной JVM, а не для общего банковского баланса в нескольких экземплярах приложения.

### 10. synchronized и мониторы

`synchronized` блокирует не метод, а монитор объекта. Обычный `synchronized`-метод эквивалентен `synchronized(this)` — использует монитор конкретного экземпляра. Два синхронизированных метода одного объекта не могут выполняться параллельно на двух потоках, но synchronized не гарантирует FIFO-порядок ожидания. Разные экземпляры имеют разные мониторы — их синхронизированные методы могут выполняться параллельно.

### 11. static synchronized

Обычный `synchronized`-метод использует монитор `this`; `static synchronized` использует монитор объекта класса (`synchronized(BankService.class)`). Следствия: два `static synchronized` метода одного класса делят общий монитор класса; `static synchronized` и обычный `synchronized` не блокируют друг друга только из-за модификаторов; разные экземпляры имеют разные мониторы для обычных synchronized-методов.

### 12. Почему synchronized не спасает в распределённой системе

Три экземпляра Spring Boot за Nginx — у каждого своя память и свои мониторы JVM. `synchronized` защищает только потоки внутри одной JVM; если два запроса попадают в разные инстансы, synchronized не обеспечит согласованность общего банковского счёта. Общие данные нескольких инстансов нужно защищать на уровне общего хранилища (БД) или другой согласованной системы — для баланса обычно транзакции и механизмы БД.

### 13. Атомарный UPDATE в PostgreSQL

`UPDATE accounts SET balance = balance - 800 WHERE id = 42 AND balance >= 800` — проверка достаточности средств и списание в одном SQL-операторе; PostgreSQL синхронизирует конкурентные обновления одной строки, при READ COMMITTED второй запрос после ожидания перепроверяет условие на актуальной версии строки. Приложение проверяет число изменённых строк (1 — успех, 0 — отказ). Удобно, когда операция укладывается в один SQL-запрос.

### 14. Почему @Transactional не решает все гонки

`@Transactional` даёт транзакционную границу, но не делает автоматически безопасной произвольную последовательность чтений и записей. При READ COMMITTED две транзакции могут прочитать один и тот же исходный баланс, обе пройти проверку и обе списать — lost update и нарушение бизнес-инвариантов. Решения: атомарный условный UPDATE (п.13) или `SELECT FOR UPDATE` внутри транзакции.

### 15. SELECT FOR UPDATE

`SELECT ... FOR UPDATE` захватывает блокировку выбранной строки — другая транзакция, которая хочет конфликтующую блокировку или изменение этой строки, ждёт. В Spring Data JPA — `@Lock(LockModeType.PESSIMISTIC_WRITE)` на запросе, вызов внутри транзакции. Важно: если перевод затрагивает несколько счетов, нужно учитывать блокировки всех изменяемых строк.

### 16. Deadlock в PostgreSQL

Deadlock — циклическое ожидание ресурсов (A держит Alice, хочет Bob; B держит Bob, хочет Alice). PostgreSQL обнаруживает deadlock и прерывает одну из транзакций с ошибкой.

Предотвращение: единый порядок захвата блокировок — например, всегда блокировать счета по возрастанию ID (`Math.min`/`Math.max` по id перед `findByIdForUpdate`). Если оба перевода (A→B и B→A) сначала блокируют счёт с меньшим ID, циклическое ожидание между ними не возникает. Ограничение: единый порядок предотвращает этот класс дедлоков только если ВСЕ операции его соблюдают; другие транзакции всё ещё могут создавать дедлоки.

### 18. Главные выводы

1. Java-приложение — долгоживущий процесс, объекты Spring переживают множество HTTP-запросов.
2. Singleton не означает thread-safe — один объект может использоваться несколькими потоками одновременно.
3. `counter++` не атомарен — возможны lost updates.
4. `volatile` не заменяет `synchronized` — видимость и атомарность разные свойства.
5. `AtomicInteger` не гарантирует корректность бизнес-операции — атомарное списание не делает атомарной проверку перед списанием (TOCTOU).
6. `synchronized` блокирует монитор, а не метод — у обычных методов это монитор экземпляра, у статических — монитор Class.
7. Блокировки JVM не распространяются на другие экземпляры приложения — в распределённой системе нужна согласованность на уровне общих ресурсов.
8. `@Transactional` не устраняет гонки автоматически — важен уровень изоляции и характер SQL-операций.
9. `SELECT FOR UPDATE` защищает строки, но может приводить к дедлокам — единый порядок захвата блокировок помогает их предотвращать.
10. Thread safety, transaction safety и distributed consistency — связанные, но разные задачи.
