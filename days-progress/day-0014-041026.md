## Сделано

- Сформулировал свою гипотезу про Skills ("просто текст, который прикрепляется заранее к промпту, и всё") и проверил её на живом материале — на списке доступных skills в текущей сессии Claude Code.
- Нашёл конкретное опровержение прямо в system-reminder: список skills в контексте содержит только имя + одну строку описания (например `code-review: Review the current diff...`), а не полное тело инструкции — значит гипотеза "весь текст уже прикреплён заранее" неверна.

## Разобрался

### Skill — не статичный текст, а процедура с ленивой загрузкой

Та же механика, что разбирали вчера на `ToolSearch` (day-0013), только применённая не к tools (функциям), а к процедурам/знаниям:

- **Всегда в контексте** — лёгкий индекс: `name` + `description` каждого skill'а (frontmatter). Этого достаточно, чтобы модель сопоставила запрос пользователя с подходящим skill'ом.
- **Подгружается по требованию** — полное тело `SKILL.md` (сами инструкции) попадает в контекст только при реальном вызове skill'а — либо явно (`/code-review`), либо когда модель сама решила, что запрос подходит под чьё-то описание.

Это тот же progressive disclosure, что и с MCP tools: не тащить всё сразу (дорого по токенам + путает выбор), а держать дешёвый каталог и догружать содержимое точечно.

### Skill физически — директория, не просто строка

```
code-review/
  SKILL.md        ← frontmatter (name, description) + сами инструкции
  references/...  ← опционально: доп. файлы, шаблоны, вспомогательные скрипты
```
Некоторые skills (`pdf`, `docx`, `xlsx` в своём списке) реально бандлят helper-скрипты (например на Python) для манипуляции файлами — это не просто markdown-инструкция для модели, а пакет из текста + исполняемого кода + шаблонов.

### Skill может запускаться не в текущем контексте, а в отдельном subagent'е

Самый сильный разрыв с гипотезой "просто текст в промпт": в описании инструмента `Skill` явно написано — *"some skills instead run in a subagent and return the finished result"*. То есть вызов skill'а иногда не добавляет текст в текущий диалог, а **запускает отдельный агент-процесс**, который работает сам по себе (возможно в фоне), и в основной разговор возвращается только готовый результат — без видимых промежуточных шагов. Это уже оркестрация выполнения, а не "подклейка промпта".

### Trade-offs — зеркально тем же, что у MCP tools (day-0013)

- Чем больше зарегистрировано skills, тем больше токенов уходит на сам индекс (имя+описание) на каждый запрос, даже если ни один не вызывается.
- Риск неверного матчинга: если описания двух skills пересекаются по смыслу, модель может выбрать не тот — тот же "needle in haystack", что и при большом числе MCP tools.

### Дистилляция моделей — не "урезание", а перенос знаний через soft labels

Student-модель обучается матчить **распределение вероятностей** teacher-модели (soft labels: "70% уверен в C, 20% в B, 10% в A"), а не только финальный правильный ответ (hard label). Это даёт student'у больше сигнала на каждом примере, чем просто human-labeled данные. Часто дистилляция делается через synthetic data: teacher генерирует миллионы примеров рассуждений, на которых с нуля обучается student.

Trade-off: student почти всегда хуже на сложных multi-step задачах (теряется "глубина" рассуждения при сжатии), но на простых/частых/однотипных задачах (классификация, экстракция) разница в качестве минимальна, а разница в цене/latency — огромная.

### Flash-модели — продуктовый тир, а не отдельная архитектура

Haiku-класс и аналоги (Gemini Flash) — облегчённые модели той же линейки, обычно получаемые через дистилляцию из старшей модели + инференс-оптимизации (quantization, меньше параметров). Назначение — не максимальное качество, а максимизация качества при фиксированном бюджете скорости/цены.

Когда юзать: задача простая и однозначная (классификация, экстракция, короткие ответы), высокий объём запросов, latency критичен, или модель — фильтр перед дорогой моделью в pipeline (роутинг по сложности: простое на Haiku, сложное эскалируется на Sonnet/Opus). Когда не юзать: multi-step reasoning, дорогая по последствиям ошибка, плохо специфицированная задача, требующая нюанса.

Важная оговорка на будущее: Anthropic не публикует точную методологию обучения Haiku относительно Sonnet/Opus — связь "Haiku = дистиллированный Sonnet" — разумное предположение по аналогии с индустрией (OpenAI mini, Gemini Flash), а не подтверждённый факт про конкретно Anthropic.

### Prompt caching — экономика и единственный инвариант

Инвариант: кэш — это **prefix match**. Любой изменённый байт в префиксе инвалидирует весь кэш после этой позиции. Порядок рендеринга фиксирован: `tools` → `system` → `messages` — стабильное (system prompt, список tools) должно идти первым, переменное (timestamp, уникальный ID, конкретный вопрос) — последним, после последней точки кэширования.

Цифры (Claude): **cache write** — ×1.25 от обычной цены input при 5-минутном TTL, ×2 при 1-часовом TTL. **Cache read** — ×0.1 от обычной цены input. Окупаемость: 5-минутный TTL окупается за 2 запроса с одним префиксом, 1-часовой — нужно минимум 3.

Частый тихий баг: `datetime.now()` в system prompt или несортированный JSON — ломает кэш без ошибки, просто `cache_read_input_tokens` всегда 0. Проверяется через `usage.cache_read_input_tokens`.

### Input vs Output в прайсинге — почему output дороже в разы

Input — текст, который модель **читает** за один проход (дешевле вычислительно). Output — текст, который модель **генерирует** токен за токеном, авторегрессивно (каждый токен — отдельный forward pass с учётом всех предыдущих) — дороже в разы (у Sonnet 5: input $2/1M, output $10/1M). Reasoning-токены (chain-of-thought scratchpad) биллятся как output, даже если не видны в финальном ответе.

Практический вывод: точный, детерминированный факт (путь к файлу, ID), данный один раз в input, почти всегда дешевле, чем позволить модели его искать через reasoning + tool calls — экономия компаундится по всему циклу (каждая лишняя итерация = полный повторный проход через весь контекст + дорогая генерация), а не просто разница в цене одного запроса.

### Длинный контекст — плюсы/минусы и "lost in the middle"

Плюсы: меньше нужды в суммаризации/RAG для задач, укладывающихся в окно, модель держит детали всего разговора/документа. Минусы: цена и latency растут линейно с объёмом контекста, выше риск упереться в лимит и запустить compaction с потерей нюанса.

**Lost in the middle** (Liu et al., Stanford/UW, 2023) — эмпирически подтверждённый эффект: в multi-document QA, если документ с правильным ответом двигать по позициям среди 20 документов, точность извлечения образует **U-образную кривую** — высокая в начале и в конце контекста, резко падает в середине (иногда ниже, чем если бы релевантного документа не было вовсе). Причина — архитектура attention и статистика тренировочных данных (важная информация в текстах чаще в начале/конце: заголовки, выводы). Параллельный публичный тест — "needle in a haystack" (Greg Kamradt): heatmap по длине контекста × глубине вставки факта, с характерной "ямой" на средних глубинах у многих моделей.

Практический вывод для RAG: релевантные чанки стоит класть не просто по убыванию ранга, а "змейкой" — топ-1 в начало, топ-2 в конец, топ-3 ближе к началу и т.д., — иначе важный факт может утонуть в середине контекста и модель его не заметит, даже если он физически там есть.
