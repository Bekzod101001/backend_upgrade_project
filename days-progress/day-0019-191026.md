## Конспект: Computer Networking — жизненный цикл HTTP-запроса

Тема: жизненный цикл HTTP-запроса и основы компьютерных сетей.

Цель: уверенно отвечать на классический вопрос собеседования — «Что происходит с HTTP-запросом от момента ввода URL в браузере до получения ответа?»

### 1. Общая последовательность HTTP-запроса

Для нового HTTPS-соединения поверх TCP:

```
1. Пользователь вводит URL
             ↓
2. DNS — определение IP-адреса
             ↓
3. TCP — установка соединения
             ↓
4. TLS — согласование шифрования
             ↓
5. HTTP — отправка запроса
             ↓
6. Reverse Proxy / Load Balancer
             ↓
7. Backend — обработка запроса
             ↓
8. Database — получение/изменение данных
             ↓
9. HTTP Response
             ↓
10. Browser — обработка ответа
```

Важно: это типичный сценарий, а не универсальная последовательность. Браузер может использовать кеш или существующее соединение. HTTP/3 работает через QUIC поверх UDP.

### 2. DNS — Domain Name System

DNS позволяет получить IP-адрес по доменному имени: `example.com → 203.0.113.10`. Домен — человекочитаемое имя ресурса, а IP — адрес, используемый для сетевой маршрутизации.

Что выяснил:

- Домен сам никуда не обращается.
- DNS-сервер — обычный сервер с IP-адресом.
- Один домен может соответствовать нескольким IP, и несколько доменов могут использовать один IP.
- DNS-записи типа `A` содержат IPv4-адреса, `AAAA` — IPv6-адреса.
- DNS может участвовать в распределении нагрузки, но DNS-балансировка и Load Balancer — разные механизмы.

```
example.com
    ├── 203.0.113.10
    ├── 203.0.113.20
    └── 203.0.113.30
```

Клиент может получить несколько IP-адресов и выбрать один для подключения.

Открытые вопросы: рекурсивное разрешение DNS; Root DNS / TLD DNS / Authoritative DNS; DNS TTL и кеширование; как браузер выбирает IP из нескольких; DNS-балансировка vs Nginx; CNAME vs A-запись.

### 3. DHCP — Dynamic Host Configuration Protocol

DHCP автоматически выдаёт устройству сетевые настройки (`IP`, `Gateway`, `DNS`). Главное открытие: **DHCP не ищет IP сайта** — он сообщает устройству, какие сетевые настройки использовать.

Типичная последовательность DHCPv4: `DISCOVER → OFFER → REQUEST → ACK`. DHCP может использовать широковещательные сообщения, поэтому устройству необязательно заранее знать IP DHCP-сервера.

Открытые вопросы: DHCP Discover на уровне сети; Default Gateway; как компьютер понимает, куда отправлять пакет для внешнего IP; DHCP lease; DHCP vs статический IP.

### 4. IP — Internet Protocol

IP отвечает за адресацию и маршрутизацию пакетов между сетями. Ключевое понимание: **IP не гарантирует доставку данных** — пакеты теряются из-за перегрузки оборудования, переполнения буферов, ошибок передачи, исчерпания TTL и других сетевых проблем.

| Характеристика | IPv4 | IPv6 |
|---|---|---|
| Размер | 32 бита | 128 бит |
| Адресов | ~4,3 млрд | ~3,4 × 10³⁸ |
| Пример | 192.168.1.1 | 2001:db8::1 |

IPv6 появился прежде всего из-за ограниченного адресного пространства IPv4.

Открытые вопросы: маршрутизация между сетями; таблица маршрутизации; CIDR (`192.168.1.0/24`); NAT; публичный vs приватный IP; связь IP и MAC-адресов.

### 5. TCP — Transmission Control Protocol

TCP — транспортный протокол, обеспечивающий надёжную и упорядоченную передачу потока байтов. Главное открытие: **TCP не знает, что именно передаёт** — для него нет понятий HTTP-запрос, JSON, файл, строка. TCP работает с байтами.

**Sequence Numbers.** TCP использует номера последовательности для отслеживания переданных байтов. Пример: `HELLO WORLD` (11 байт в UTF-8):

```
SEQ 1000 → HELLO
SEQ 1005 → " WOR"
SEQ 1009 → LD
```

Если потеряется второй сегмент, TCP обнаружит отсутствие байтов и организует повторную передачу. ACK подтверждает получение данных.

**Three-Way Handshake:**

```
Client                 Server
   │                      │
   │──── SYN ────────────►│
   │◄─── SYN-ACK ─────────│
   │──── ACK ────────────►│
   │                      │
       ESTABLISHED
```

SYN — инициирование соединения, SYN-ACK — ответ сервера, ACK — подтверждение клиента. Handshake также позволяет согласовать начальные номера последовательности и параметры соединения. Если последний ACK потеряется, сервер может повторно отправить SYN-ACK.

**Порты и сокеты.** IP определяет сетевой адрес назначения, TCP использует порты для доставки данных нужному приложению:

```
192.168.1.20:8080 → Spring Boot
192.168.1.20:9000 → PHP
```

TCP-соединение идентифицируется комбинацией `Source IP + Source Port + Destination IP + Destination Port`.

Открытые вопросы: TCP vs UDP; TCP Window Size; Flow Control; Congestion Control; как TCP определяет потерю сегмента; Retransmission Timeout; закрытие TCP-соединения; `TIME_WAIT`; TCP-соединение vs HTTP-сессия.

### 6. HTTP и TCP — разные уровни

TCP отвечает за передачу байтов, HTTP определяет смысл передаваемых сообщений:

```
GET /users/123 HTTP/1.1
Host: example.com
```

TCP не понимает `GET`, `/users/123` или `Host` — для него это последовательность байтов. HTTP определяет, как интерпретировать запрос и формировать ответ. HTTP/1.1 и HTTP/2 обычно используют TCP, HTTP/3 использует QUIC поверх UDP.

Открытые вопросы: HTTP/1.1 vs HTTP/2; почему HTTP/3 использует QUIC; HTTP Keep-Alive; HTTP Multiplexing; как сервер определяет границы HTTP-запроса; заголовки и тело запроса.

### 7. Reverse Proxy и Load Balancer

Один IP может обслуживать несколько доменов:

```
example.com     → 203.0.113.10
api.example.com → 203.0.113.10
```

Nginx различает запросы по имени хоста: в HTTP/1.1 — через заголовок `Host`, при HTTPS имя сервера также может передаваться через TLS SNI.

```
Client
   ↓
Nginx :443
   ├── example.com     → Frontend :3000
   └── api.example.com → Backend :8080
```

Открытые вопросы: Reverse Proxy vs Forward Proxy; алгоритмы балансировки Nginx; TLS Termination; как Load Balancer определяет недоступность backend; что происходит с запросом при падении backend-инстанса.

### 8. TLS — Transport Layer Security

TLS обеспечивает защищённую передачу данных: шифрование, проверка подлинности сервера, защита целостности данных.

```
HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP
```

**Обмен ключами Диффи — Хеллмана.** Клиент и сервер могут согласовать общий секрет, не передавая сам секрет по сети. Упрощённый пример (маленькие числа, только для обучения, криптографически небезопасен):

```
Публичные параметры: p = 23, g = 5

Клиент: a = 6 (секрет) → A = 5⁶ mod 23 = 8
Сервер: b = 15 (секрет) → B = 5¹⁵ mod 23 = 19

Обмен публичными A и B, затем независимый расчёт общего секрета:
Клиент: 19⁶ mod 23 = 2
Сервер: 8¹⁵ mod 23 = 2
```

Результат одинаковый с обеих сторон. В TLS 1.3 обычно применяется ECDHE. Сертификаты подтверждают подлинность сервера и защищают от MITM-атак.

Открытые вопросы: симметричное vs асимметричное шифрование; почему публичный ключ не позволяет расшифровать HTTPS-трафик; приватный/публичный ключ; TLS-сертификат; Certificate Authority; как браузер проверяет сертификат; MITM; Perfect Forward Secrecy; как TLS получает ключи шифрования из общего секрета.

### 9. Итоги занятия

**Что удалось понять:**

- DNS и DHCP решают совершенно разные задачи.
- DNS-серверы имеют собственные IP-адреса; один домен может иметь несколько IP.
- IP отвечает за адресацию и маршрутизацию, TCP — за надёжную передачу байтов.
- TCP не знает содержимого HTTP-запроса; данные можно передавать через TCP без HTTP.
- TCP использует Sequence Numbers и ACK, устанавливает соединение через Three-Way Handshake.
- IP и порт позволяют направить данные нужному приложению; Nginx может обслуживать несколько доменов через один IP и порт.
- TLS позволяет согласовать ключи шифрования без передачи общего секрета открытым текстом.

**Что требует закрепления** (по приоритету):

1. Сетевой фундамент: IP, маршрутизация, Gateway, TCP, UDP, сокеты, передача данных через несколько сетей.
2. Безопасность: TLS Handshake, симметричное/асимметричное шифрование, сертификаты и центры доверия.
3. Backend Infrastructure: Reverse Proxy, Load Balancer, HTTP/1.1 / HTTP/2 / HTTP/3, Connection Pooling и Keep-Alive.

**Критерий успешного освоения:** за 3–5 минут последовательно объяснить `DNS → TCP → TLS → HTTP → Reverse Proxy → Backend → Database → HTTP Response → Browser` и ответить на уточняющие вопросы по каждому компоненту.

Текущий статус: базовая концептуальная картина сформирована. TCP и DNS стали понятнее; маршрутизация IP и криптография TLS требуют дополнительного изучения.
