## Разобрался

- **Почему `@Transactional` не спас.** Каждая транзакция атомарна сама по себе, но 10 транзакций прочитали одно и то же значение 1 000 000 (Postgres по умолчанию `READ COMMITTED`). Hibernate отправляет `UPDATE accounts SET balance = 80000000`, то есть **готовое число, посчитанное в Java по устаревшему чтению**. Каждая запись затёрла предыдущую: это **lost update**.
- **Зачем блокировки, если «попасть в миллисекунды невозможно»** (мой скепсис):
  - окно гонки — не момент вызова, а вся транзакция от `SELECT` до `COMMIT`: 5–10 ms в покое, сотни ms под нагрузкой или с внешним вызовом внутри транзакции;
  - пересечения порождает сама система: двойной клик; retry по таймауту (пересекается с исходным запросом по определению); горячий счёт мерчанта с десятками оплат в секунду; батчи; атакующий, намеренно шлющий пачку запросов;
  - при миллионе операций «один на миллион» случается каждый день, причём тихо: ошибок нет, всплывает на сверке;
  - row-level lock дешёвый: блокирует одну строку, ждут только операции над тем же счётом.
- **Lock не спасает от повтора одного и того же запроса.** Retry выполнится последовательно, и деньги спишутся дважды. Для этого нужна idempotency.
- **`SELECT ... FOR UPDATE`:** читает строку и ставит row-level lock до `COMMIT`/`ROLLBACK`. Другие `FOR UPDATE`, `UPDATE` и `DELETE` на этой строке ждут. После commit ждущий получает свежую версию.
- **MVCC:** Postgres не правит строку на месте, а создаёт новую версию. Обычный `SELECT` не ждёт и читает последнюю закоммиченную версию. Читатели не блокируют писателей, писатели не блокируют читателей.
  - Следствие: lock работает, **только если его берут все**, кто читает значение, чтобы потом его изменить. Один путь с обычным `SELECT` возвращает lost update.
- **`FOR UPDATE` нужен не всегда**, а только в паттерне read → решение в Java → write:

  | Что делаю | Что нужно |
  |---|---|
  | только читаю, чтобы показать | обычный `SELECT` |
  | читаю → решаю/считаю в Java → пишу | `SELECT ... FOR UPDATE` или `@Version` |
  | изменение выражается одним условным UPDATE | атомарный `UPDATE ... SET x = x - ? WHERE ... AND x >= ?` |

- **Моё заблуждение:** «достаточно сделать UPDATE, и дальше всё проверится по нему». В Java-версии это не работает: UPDATE честно ждёт lock, но в `SET` уже вписано число, посчитанное по старому чтению. Работает, только если новое значение и проверку считает **сама база** в UPDATE.
- **Атомарный UPDATE:** `balance` в `SET`/`WHERE` — не число, запомненное заранее, а значение строки в момент записи. Чтение, проверка и запись проходят одной операцией под lock'ом. Результат — число затронутых строк: `1` значит списали, `0` значит не хватило.
- **Что делает второй UPDATE, если строка залочена:**
  - ждёт окончания первой транзакции;
  - после `COMMIT` берёт новую закоммиченную версию и **заново проверяет `WHERE`**;
  - после `ROLLBACK` берёт исходную строку.

  Сценарии (два списания по 600 000):

  | Баланс | Tx1 | Tx2 видит | Tx2 | Итог |
  |---|---|---|---|---|
  | 1 000 000 | `COMMIT` | 400 000 | `UPDATE 0` | 400 000 |
  | 1 200 000 | `COMMIT` | 600 000 | `UPDATE 1` | 0 |
  | 1 000 000 | `ROLLBACK` | 1 000 000 | `UPDATE 1` | 400 000 |

  На `REPEATABLE READ` Tx2 в первом сценарии упала бы с `could not serialize access due to concurrent update`, а не работала бы по старым данным.
- **«Одновременно» для одной строки не бывает:** захват row lock внутри Postgres атомарный, пускает строго одного, остальные встают в очередь. Как турникет в метро.
- **Trade-offs:**
  - `FOR UPDATE`: просто, гарантия, без повторов; горячий счёт становится очередью, ждущие держат соединения из пула;
  - атомарный UPDATE: самый дешёвый и надёжный, но только пока логика помещается в `WHERE`. Лимиты, статусы, комиссии и история операций туда не лезут;
  - в production: deadlock при встречных A→B / B→A (лечится захватом в порядке `id`), долгая транзакция держит lock и выжирает пул, нужен `lock_timeout` / `NOWAIT` / `SKIP LOCKED`.
- **На интервью:**
  - *«Зачем блокировки, если одновременные запросы редки?»* Они не редки: retry по таймауту пересекается с исходным запросом, горячие счета всегда под параллельной нагрузкой, race condition эксплуатируют намеренно. Для денег нужна гарантия, а не вероятность.
  - *«Блокирует ли `SELECT ... FOR UPDATE` обычный `SELECT` в Postgres?»* Нет, из-за MVCC.
  - *«Условный UPDATE или lock?»* Если инвариант выражается одним UPDATE, то условный UPDATE. Если нужна логика в приложении, то pessimistic lock или `@Version`.
