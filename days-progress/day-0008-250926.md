## Разобрался

### `@Scheduled` пингует каждую секунду вхолостую — и это ок

Спросил: не дорого ли дёргать outbox-таблицу каждую секунду, даже когда там пусто?

Дорого — нет, посчитано конкретно: запрос `SELECT ... WHERE processed_at IS NULL` идёт по частичному индексу (`idx_outbox_unprocessed`, сделан ещё в Day 7 миграции) — доли миллисекунды на пустой таблице, не full scan. Раз в секунду × доли мс — не видно на графиках. Дорого polling становится не из-за самого факта опроса, а при: запросе без индекса на больших таблицах, слишком частом интервале (мс, а не секунды), или множестве таких воркеров одновременно (вот тут окупается Debezium вместо polling).

Полезная параллель: Laravel `queue:work` с драйвером `database` делает ровно то же самое — `while(true) { pop(); if empty sleep(3); }`. Polling — не экзотика, обычный паттерн, просто раньше не видел его в терминах.

### Что реально лежит под `@Scheduled` — три слоя, без магии

```
1. Старт приложения:
   ScheduledAnnotationBeanPostProcessor (сам бин) сканирует все бины,
   находит методы с @Scheduled, регистрирует как задачи

2. Планировщик:
   ThreadPoolTaskScheduler — тонкая обёртка Spring вокруг
   java.util.concurrent.ScheduledThreadPoolExecutor (обычный класс JDK,
   тот же механизм, что setTimeout/setInterval, просто в отдельном пуле потоков)

3. Вызов:
   когда время пришло — ScheduledMethodRunnable.run() → method.invoke(bean)
   (обычная рефлексия, то же самое, чем Spring вызывает @GetMapping)
   если метод @Transactional — вызов идёт через AOP-прокси,
   который открывает транзакцию ДО настоящего метода и коммитит ПОСЛЕ
```

Классы подтвердил через `unzip -l`/`javap` по jar'никам, не поверил на слово: `ScheduledAnnotationBeanPostProcessor`, `ThreadPoolTaskScheduler`, `ScheduledMethodRunnable` — все реально существуют в `spring-context-7.0.9.jar`.

Итог: `OutboxRelay` — не отдельный процесс (в отличие от Laravel `queue:work`, который ты запускаешь отдельной командой). Это обычный Spring-бин внутри того же JVM, что и веб-сервер — просто триггер не HTTP-запрос, а тикающие часы на отдельном потоке `scheduling-1`.

### Bean — объект, которого ты не создавал сам

Модель: в Laravel ты пишешь `__construct(TransferService $service)` в контроллере и не вызываешь `new TransferService(...)` нигде — Laravel service container резолвит сам. Spring-бин — то же самое, просто другое слово.

```
Spring сканирует пакеты (@ComponentScan из @SpringBootApplication)
  → находит @Service/@Component/@Repository/@RestController/@Configuration+@Bean
  → строит bean definition (рецепт: класс + что нужно в конструктор + scope)
  → строит граф зависимостей, создаёт в топологическом порядке через рефлексию
```

На своём коде: `TransferExecutor` создаётся раньше `TransferService`, потому что `TransferService` просит его в конструктор — Spring это определяет сам, порядок нигде руками не писан.

**Подвох против Laravel-интуиции:** дефолтный scope у Spring-бина — **singleton** (один объект на всё приложение навсегда), у Laravel-биндинга без `->singleton()` — наоборот, новый объект на каждый resolve. Поэтому все поля бинов в MiniBank — `private final`: singleton расшарен между всеми одновременными запросами из разных потоков, мутабельное состояние в поле сервиса — гарантированная гонка данных.

Вчерашний баг («No qualifying bean of type KafkaTemplate») теперь объясняется этим же словарём: контейнер искал кандидата по типу среди зарегистрированных бинов и не нашёл подходящего — тот же механизм, что я только что описал, просто на этапе старта, а не рантайма.

### IoC и «контейнер» — почему это не просто красивое слово

**Модель:** без фреймворка ты сам вызываешь `new` в правильном порядке и сам решаешь, когда вызвать метод — контроль у твоего кода. С IoC контроль переходит framework'у: framework создаёт твои объекты и framework решает, когда позвать твой код (HTTP-запрос → контроллер, таймер → `@Scheduled`, сообщение → `@KafkaListener`). Классическая формулировка — Hollywood Principle: *«Don't call us, we'll call you»*.

**Почему «контейнер»** — не метафора, реальный объект. Доказал тестом (написал, прогнал, сразу удалил — в проекте не остался):
```java
ApplicationContext context;
context.getBean(TransferService.class) == context.getBean(TransferService.class)  // true

=== IoC-контейнер — это реальный объект в памяти ===
всего бинов в контейнере:     410
дважды дал ОДИН И ТОТ ЖЕ объект: true
```
`ApplicationContext` физически хранит `Map<имя бина → готовый экземпляр>` — контейнер в буквальном смысле держит объекты, как коробка вещи, управляет их полным жизненным циклом (создание → wiring → `@PostConstruct` → ... → `@PreDestroy`).

### DI и IoC — независимые понятия, а не «DI это способ IoC» (моя неточность вчера)

Мой вчерашний тезис «DI — способ реализации IoC» был неточным, поймано правильным вопросом. Разобрались до конца:

**DI без IoC существует** — «pure DI», ручная сборка без всякого фреймворка:
```java
AccountRepository repo = new AccountRepositoryImpl(dataSource);
TransferExecutor executor = new TransferExecutor(repo, ...);   // зависимость внедрена, framework не участвует
```
Зависимость внедрена снаружи (не `new` внутри себя, не lookup) — формально DI. Но control целиком у вызывающего кода — framework никому не звонит. Значит DI без IoC — реален.

**IoC без DI тоже существует** — на своём же коде:
```java
@KafkaListener(topics = ..., groupId = "notification")
void onTransferCompleted(TransferCompletedEvent event) { ... }
```
Framework сам зовёт метод (IoC) — но `event` не инжектится как зависимость, это аргумент конкретного вызова. Ещё пример — **Service Locator pattern** (J2EE до DI): `ServiceLocator.lookup("AccountRepository")` — тоже IoC в широком смысле (объект не создаёт зависимость через `new`), но не DI (зависимость не подсовывается снаружи, объект сам идёт и ищет).

Матрица 2×2:
```
                DI                    НЕТ DI
IoC       Spring @Autowired      @KafkaListener, @Scheduled,
          конструкторы               Service Locator

НЕТ IoC   ручной DI в main()     new AccountRepositoryImpl()
                                  прямо внутри класса
```

**Откуда путаница — исторически, не случайно.** Martin Fowler, 2004, статья «Inversion of Control Containers and the Dependency Injection pattern»: термин IoC к тому моменту стал слишком общим (под него подпадает вообще всё, где framework зовёт твой код — Service Locator, Template Method, серверные callback'и), поэтому он предложил более узкий термин DI конкретно для механизма, который выбрали новые контейнеры (PicoContainer, позже Spring). Spring построил себя вокруг DI как основного способа реализации IoC — отсюда и историческое слияние терминов в разговорной речи, хотя логически они ортогональны.

**Точная формулировка для интервью:** IoC — принцип («кто управляет вызовом кода»), DI — конкретная техника («как объект получает зависимости»). Пересекаются только потому, что Spring выбрал DI основным механизмом реализации IoC — не в силу логической необходимости.
