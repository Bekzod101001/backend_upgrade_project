## Конспект: SOLID, ACID и транзакции PostgreSQL

### SOLID — пять принципов проектирования

SOLID — набор принципов ООП-проектирования для поддерживаемого, расширяемого и слабо связанного кода. Это рекомендации, а не строгие законы.

- **S — Single Responsibility.** Модуль должен иметь одну ответственность — одну основную причину изменения. Ответственность не равна одному методу: класс может содержать десятки методов, если они обслуживают одну связанную ответственность. Ключевой вопрос: по каким независимым причинам придётся изменять этот класс?
- **O — Open/Closed.** Сущности должны быть открыты для расширения, но закрыты для модификации — новые варианты поведения добавляются без изменения стабильной логики. Пример: вместо `if/else` для Click/Payme/Stripe — интерфейс `PaymentProcessor` и отдельные реализации (Strategy).
- **L — Liskov Substitution.** Подтип должен быть взаимозаменяем с базовым типом без нарушения его поведенческого контракта: предусловия, постусловия, инварианты, гарантии ошибок. Пример нарушения: `Storage.save()` обещает, что после успешного возврата файл доступен для чтения, а асинхронная реализация возвращает ID до фактического сохранения.
- **I — Interface Segregation.** Клиент не должен зависеть от методов интерфейса, которые ему не нужны. Вместо одного интерфейса с `sendEmail/sendSms/sendPush` — отдельные `EmailSender`, `SmsSender`, `PushSender`. SRP про разделение ответственностей модулей, ISP — про разделение контрактов для их потребителей.
- **D — Dependency Inversion.** Высокоуровневые модули (бизнес-логика, `OrderService`) не должны зависеть от низкоуровневых (`PostgresOrderRepository`) — оба зависят от абстракции (`OrderRepository`). DIP — принцип направления зависимостей, DI — передача зависимостей извне, IoC — передача управления внешнему механизму (Spring). Spring DI не гарантирует DIP: даже с конструкторной инъекцией сервис может зависеть от конкретной инфраструктурной реализации. Composition Root — место сборки зависимостей (в Spring часто `@Bean`-конфигурация).

### ACID — свойства транзакций

- **Atomicity.** Транзакция выполняется целиком или откатывается. `@Transactional` в Spring не откатывает автоматически внешний HTTP-платёж, Kafka-сообщение или другую независимую систему.
- **Consistency.** Транзакция переводит базу из одного допустимого состояния в другое, сохраняя инварианты — через `CHECK`/`UNIQUE`/`FOREIGN KEY`/`NOT NULL` плюс бизнес-логику плюс корректную обработку конкурентности. База не знает правил, которые нигде не выражены.
- **Isolation.** Определяет допустимые эффекты конкурентного выполнения. В PostgreSQL: READ UNCOMMITTED фактически = READ COMMITTED; READ COMMITTED (default) — каждый оператор видит свой снимок закоммиченных данных; REPEATABLE READ — стабильный снимок на всю транзакцию, часть конфликтов → ошибка; SERIALIZABLE — результат эквивалентен какому-то последовательному порядку (но выполнение физически параллельное, PostgreSQL отслеживает опасные зависимости и прерывает одну транзакцию `SQLSTATE 40001`, после которой нужен повтор всей транзакции).
- **Durability.** После COMMIT изменения сохраняются даже при сбое процесса/сервера. PostgreSQL использует WAL (Write-Ahead Log): нужные записи журнала сохраняются раньше, чем страницы данных обязаны попасть на диск. Нюансы: `synchronous_commit`, надёжность оборудования, потеря самого хранилища.

### MVCC и блокировки в PostgreSQL — как это соотносится с нашим deadlock'ом

- MVCC: версии строк позволяют обычным чтениям идти параллельно с изменениями — `SELECT` не ждёт блокировку, которую держит `UPDATE`/`FOR UPDATE`, а видит последнюю закоммиченную версию.
- `SELECT ... FOR UPDATE` — то же самое, что `findByIdForUpdate()` в `TransferService` (см. day-0004): блокирует строку до конца транзакции, препятствуя конфликтующим операциям.
- Простой `UPDATE balance = balance - amount WHERE id = ...` сам лочит строку — отдельный `FOR UPDATE` не нужен для чистой арифметики (альтернативный способ фикса lost update из TODO day-0004).
- **Lost update без блокировки**: если обе транзакции сначала читают баланс, затем пишут заранее рассчитанное значение — вторая запись затирает первую. Решения: атомарный `UPDATE`, `SELECT FOR UPDATE` (то, что уже сделано), optimistic locking через `@Version`, более строгая изоляция.
- Атомарная проверка баланса прямо в `UPDATE ... WHERE balance >= amount` — альтернатива pessimistic lock: приложение должно проверять количество изменённых строк.

### Транзакции и внешние системы (за пределами PostgreSQL)

Если `@Transactional`-метод делает внешний HTTP-платёж и затем падает при сохранении заказа, PostgreSQL откатит свою транзакцию, но платёж не отменится сам. Для таких случаев: **Idempotency Key** (повторы обрабатываются безопасно — см. day-0005), **Transactional Outbox** (бизнес-изменение и событие в outbox-таблице — одна транзакция, отдельный процесс публикует в Kafka), **Saga** (координация локальных транзакций с компенсациями), **Reconciliation** (сверка состояния, когда результат операции неизвестен — типичные статусы `PENDING/PROCESSING/COMPLETED/FAILED/UNKNOWN`).

## Разобрался

- Главный итог сессии: SOLID отвечает на «как организовать код, чтобы его было проще менять», ACID — «какие гарантии даёт транзакция», MVCC/locking — «как Postgres обрабатывает конкурентность», а idempotency/outbox/saga — «как работать с процессами за пределами одной транзакции БД».
