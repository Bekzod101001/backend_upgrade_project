## Разобрался

### Живая трасса одного перевода — три независимых потока, связанных только через БД и Kafka

```
curl → HTTP-поток [nio-8081-exec-1]:
  INSERT transfers → FOR UPDATE lock Alice+Bob → INSERT outbox (ТА ЖЕ транзакция) → UPDATE балансов → COMMIT
  → клиент получил 200 за ~80 мс, про Kafka ничего не знает

  ... пауза ~900 мс ...

фоновый поток [scheduling-1] — тот самый @Scheduled из Day 8:
  проснулся САМ (никто не звал), SELECT ... SKIP LOCKED нашёл строку →
  поднял Kafka producer → отправил → пометил processed_at

ещё один, ТРЕТИЙ поток [ntainer#0-0-C-1] — Kafka consumer, живёт с самого старта приложения:
  выловил сообщение → "SMS: на счёт 2 поступило 100000 тийин"
```

Три потока, ни один не вызывал другой напрямую — только через БД (outbox) и через Kafka. Это и есть **temporal decoupling** своими глазами, а не на словах: HTTP-запрос закончился и ответил клиенту, вся цепочка Kafka ещё не началась.

### Kafka CLI — живые команды, подтверждающие теорию прошлых дней

```bash
# скрипты живут ВНУТРИ контейнера, не на хосте — лечится через docker exec
docker exec minibank-kafka-1 /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic transfer.completed --from-beginning

docker exec minibank-kafka-1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic transfer.completed

docker exec minibank-kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group notification
```

Реальный вывод `--describe` по топику:
```
PartitionCount: 3  ReplicationFactor: 1
Partition: 0  Leader: 1  Replicas: 1  Isr: 1
Partition: 1  Leader: 1  Replicas: 1  Isr: 1
Partition: 2  Leader: 1  Replicas: 1  Isr: 1
```
`Leader`/`Replicas`/`Isr` все равны `1`, потому что в dev-кластере один-единственный брокер — ему просто некуда деться, он лидер всего. В проде `Replicas` показал бы несколько разных брокеров, а разрыв между `Replicas` и `Isr` (реплика отстала, не синхронизирована) — это и есть индикатор under-replicated партиции, про который говорили в контексте прод-инцидентов (Day 11).

Реальный вывод `--describe` по consumer group:
```
partition 0:  CURRENT-OFFSET=1  LOG-END-OFFSET=1  LAG=0
partition 1:  CURRENT-OFFSET=-  LOG-END-OFFSET=0  LAG=-
partition 2:  CURRENT-OFFSET=-  LOG-END-OFFSET=0  LAG=-
```
Наглядное разделение committed offset (свойство ГРУППЫ) от log-end-offset (свойство ПАРТИЦИИ) — то, что в начале блока про Kafka путалось в словах, здесь видно в колонках напрямую. `LAG` — разница между ними, растущий `LAG` при зависшем `CURRENT-OFFSET` и растущем `LOG-END-OFFSET` — это и есть consumer lag, метрика, которой в MiniBank пока нет (TODO c Day 7), но которая доступна из коробки через этот же CLI.

### Заблуждение 1: партиции создаются динамически под ID записи

Предположение: раз ключ партиционирования — `account_id`, значит под каждый новый `account_id` создаётся новая партиция.

Неверно, и проверено не на словах, а реальным алгоритмом Kafka (`org.apache.kafka.common.utils.Utils.murmur2`, скомпилировано и прогнано отдельно):
```
account_id=1    -> murmur2=154038159    -> partition 0
account_id=2    -> murmur2=648968168    -> partition 2
account_id=3    -> murmur2=999318143    -> partition 2
account_id=4    -> murmur2=1514888353   -> partition 1
account_id=5    -> murmur2=55100550     -> partition 0
account_id=999  -> murmur2=2115548775   -> partition 0
```
Партиций ровно 3 (как объявлено в `KafkaTopics.java` через `.partitions(3)`) — число фиксировано ОДИН РАЗ при создании топика. Ключ не создаёт новую партицию, а маршрутизирует (`hash(key) % partition_count`) в одну из уже существующих. `account_id=2` и `=3` оба попали в partition 2 — разные счета делят одну партицию, и это нормально: порядок между разными счетами никогда и не был нужен.

Две причины, почему число партиций не растёт автоматически под нагрузку:
1. **Рост числа партиций меняет результат `% N` для почти всех ключей** — старые сообщения счёта остаются в старой партиции (их никто не переносит), новые события того же счёта после ресайза пойдут в другую партицию — порядок событий одного счёта разваливается в момент ресайза. Это и есть факт из Day 6 про «добавить можно, убавить нельзя, добавление ломает привязку ключ→партиция» — теперь видно, почему именно.
2. **Партиция — не бесплатная абстракция**, а реальный файл + реплики + поток репликации на каждом брокере. «Одна партиция на сущность» на миллионах ID убила бы брокеры мгновенно (реальный эксплуатационный лимит в несколько тысяч партиций на брокер).

### Заблуждение 2: партиции существуют, чтобы файлы не разрастались

Предположение: партиции нужны, чтобы один файл не стал слишком большим.

Неверно — и у Kafka уже есть отдельный, не связанный с партициями механизм именно под это: **сегменты**. Нашёл на реальном диске контейнера:
```
docker exec minibank-kafka-1 ls -la /tmp/kafka-logs/transfer.completed-0/

00000000000000000000.index       10485760 байт (разреженный индекс offset → позиция в файле)
00000000000000000000.log              240 байт (сами данные — пока одно сообщение)
00000000000000000000.timeindex   10485756 байт (индекс по времени)
```
Имя файла — offset первого сообщения в сегменте. Партиция физически состоит не из одного бесконечного файла, а из **серии сегментов** — когда текущий `.log` дорастает до лимита (`log.segment.bytes`, по умолчанию 1 ГБ) или возраста (`log.roll.hours`), Kafka закрывает его и открывает новый с именем следующего offset. **Retention работает на уровне сегментов** — удаляется целый старый файл, а не вычищаются отдельные строки внутри одного гигантского файла.

Вывод: было бы у нас хоть 1 партиция, хоть 100 — сегменты ротировались бы одинаково, файлы не разрастались бы бесконечно в любом случае. **Партиции решают throughput/параллелизм** (сколько писателей и consumer'ов могут работать одновременно), а не размер на диске — это две независимые задачи, которые до этого сливались в одну интуицию.
