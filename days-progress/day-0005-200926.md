## Разобрался

- **Idempotency ≠ concurrency.** Проверка, которая разделяет:
  ```
  убрать конкурентность (1 поток, пауза 30 с между запросами) → баг ОСТАЁТСЯ
  убрать retry (1000 потоков, у каждого свой перевод)         → бага НЕТ
  ```
  Значит причина — retry, а не одновременность, и лечится она не инструментами конкурентности. `lost update` — аномалия модели изоляции, у неё есть имя и уровень, который её запрещает. Двойного списания в этой классификации нет вообще: база отработала корректно.
- **Почему не спасёт даже `SERIALIZABLE`:** он гарантирует эквивалентность *какому-то* последовательному порядку, а здесь два перевода и правда выполнились последовательно — валидная история.
- **Задача не «отсечь одинаковые запросы», а «отличить одно намерение от двух».**
  ```
  A: Алиса нажала «перевести», сеть отвалилась, клиент ретраит  → провести 1
  B: Алиса перевела, через минуту перевела ещё раз то же самое  → провести 2
  ```
  Payload побайтово одинаковый. По содержимому неразличимо — нужен идентификатор намерения.
- **Ключ генерирует клиент**, и генерирует его на **намерение**, а не на HTTP-запрос:
  ```js
  const key = crypto.randomUUID();          // ✅ при открытии формы, снаружи попытки
  async function submit() { ... headers: {'Idempotency-Key': key} }

  async function submit() {                  // ❌ новый UUID на каждый retry — защиты нет
    ... headers: {'Idempotency-Key': crypto.randomUUID()}
  }
  ```
  Сервер не может генерить ключ сам: для него две попытки неразличимы, это и есть исходная проблема.
- **Клиент не человек — то же правило.** Kafka consumer → `event_id` сообщения; сервис → сервис → id инициировавшей операции; batch-файл → id файла + номер строки. Ключ должен быть свойством **события**, а не попытки его обработать. Часто ключ уже есть в бизнес-данных (`order_id`, номер платёжного поручения) — **natural idempotency key**, он лучше искусственного, его невозможно «забыть сохранить между попытками».
- **Двухфазная схема (`POST /transfers/init` → ключ от сервера)** — рабочий паттерн (Stripe PaymentIntent), но защищает не тем, чем кажется: `/init` точно так же может быть доставлен дважды, просто он не двигает деньги, поэтому лишние ключи — мусор, а не двойное списание. Если UI дёргает `/init` на каждый тап — дыра возвращается. Реальная польза: клиент физически не может «сгенерить новый UUID на каждый retry». Цена — round trip и state machine.
- **Клиент может облажаться, и часть этого сервер не поймает никогда:**

  | Что сделал клиент | Ловит ли сервер |
  |---|---|
  | не прислал заголовок / не-UUID | ✅ `400` |
  | **новый ключ на каждый retry** | ❌ **никогда** |
  | тот же ключ, другой payload | ✅ `IdempotencyKeyConflictException` |
  | чужой ключ | ✅ скоуп по владельцу (у нас пока нет auth) |

  Рамка: идемпотентность — **контракт двух сторон**. Сервер обещает «один ключ = одна операция», клиент обещает «одно намерение = один ключ». Сервер не может выполнить обязательство клиента, это граница системы, а не дыра в дизайне.
- **Почему нельзя решить задачу привычным `SELECT ... FOR UPDATE` по ключу:** **нельзя заблокировать то, чего нет**. По несуществующему ключу запрос вернёт ноль строк и заблокирует ноль строк — две транзакции одновременно увидят пустоту и обе вставят. Это же и есть точный ответ, почему `if (existsByIdempotencyKey(key))` не работает: не «проверка неатомарна» абстрактно, а **у отсутствия строки нет замка**.
  - Кто умеет «блокировать несуществующее»: `UNIQUE` индекс (наш выбор), advisory lock (`pg_advisory_xact_lock(hashtext(key))`), `SERIALIZABLE` (predicate locks, платишь откатами).
- **`UNIQUE` — это не настройка, а физический индекс.** `\d transfers` показывает: `"transfers_idempotency_key_key" UNIQUE CONSTRAINT, btree (idempotency_key)`. Иначе никак: проверка уникальности = поиск, а поиск по 50 млн строк на каждую вставку нереален.
- **`COMMIT` ничего не записывает.** Ломающее заблуждение: изменения не копятся в памяти до commit. `INSERT` кладёт строку в таблицу **сразу**, `COMMIT` лишь отмечает «транзакция №757 завершилась успешно», и её записи разом становятся видимыми.
- **`xmin` / `xmax` / MVCC.** У каждой строки есть скрытые колонки (`SELECT xmin, xmax, * FROM accounts`): `xmin` — номер транзакции-автора, `xmax` — номер удалившей (0 = жива). Правило видимости: вижу строку, если её автор уже закоммитился. `UPDATE` не правит строку на месте, а пишет новую версию — отсюда «читатели не блокируют писателей».
- **Почему `INSERT` умеет ждать без единой написанной блокировки:** проверка уникальности **не может** пользоваться видимостью. Иначе вторая транзакция не увидела бы чужой незакоммиченный ключ, вставила бы свой, и в уникальном индексе оказалось бы два одинаковых значения. Значит проверка смотрит на физическое наличие, включая незакоммиченное, — и упирается в конфликт, автор которого ещё не решил свою судьбу:
  ```
  A закоммитится → дубль    → B должен упасть
  A откатится    → дубля нет → B должен вставить
  Ответ зависит от будущего → угадать нельзя → ждать.
  ```
- **`INSERT` — это не «автоматический `FOR UPDATE`», а `UPDATE` — почти буквально он.** Разбор с матрицей режимов и экспериментом — в разделе «Блокировки, которые никто не писал».
- **Через unique index возможен deadlock**, хотя `FOR UPDATE` в коде нет: `T1: INSERT A, INSERT B` против `T2: INSERT B, INSERT A` → тот же цикл, тот же `40P01`, то же лечение единым порядком.
- **Почему `INSERT` стоит первым в транзакции:** дубль отваливается на самой дешёвой операции и **ничего не держит**, пока спит на индексе — счета остаются свободными для остальных переводов. Поставь `INSERT` в конец — ждущий дубль висел бы с lock'ами на обоих счетах. Работает благодаря `GenerationType.IDENTITY`: Hibernate обязан выполнить `INSERT` немедленно, чтобы получить `id`, и не может отложить его до commit.
- **Почему обработка повтора обязана быть снаружи транзакции:** после `unique_violation` транзакция помечена rollback-only, следующий запрос в ней получит `current transaction is aborted`. Результат первой попытки надо читать в **новой** транзакции. Отсюда и два бина.
- **Self-invocation:** нельзя просто вынести `execute()` методом того же класса — `@Transactional` работает через прокси, при вызове `this.execute()` прокси не участвует и аннотация молча не срабатывает.
- **`orElseThrow(() -> e)` — не украшение.** `DataIntegrityViolationException` бросает и FK на несуществующий счёт. Если записи по ключу нет — упало что-то другое, надо пробросить исходное исключение, а не выдавать чужую ошибку за дубль.
- **`CountDownLatch` в конкурентных тестах** — шлагбаум со счётчиком, который только уменьшается; дошёл до нуля — открыт навсегда, сбросить нельзя. Два в одном тесте:
  - `start = new CountDownLatch(1)`: все потоки встают на `start.await()`, main делает `countDown()` → срываются одновременно. Без него потоки успевали бы отработать по очереди (создание потока дольше перевода), и тест доказывал бы ноль;
  - `done = new CountDownLatch(threads)`: `countDown()` строго в `finally` (иначе упавший поток оставит счётчик ненулевым и `await()` повиснет навсегда), а ждём через `assertThat(done.await(30, SECONDS)).isTrue()` — голый `await()` превратил бы зависание в вечный тест вместо красного.
  - В Java 21 `ExecutorService` стал `AutoCloseable` и `close()` сам ждёт завершения задач, но молча и без таймаута — поэтому `done` оставляем.
  - Родня: `CyclicBarrier` — многоразовый, потоки ждут друг друга; `Semaphore` — пропускает не больше N.
- **На интервью:**
  - *«Как защититься от двойного списания при retry?»* Idempotency key от клиента + `UNIQUE constraint` в той же транзакции, что и операция.
  - *«Почему не `SELECT FOR UPDATE` по ключу?»* Нельзя залочить несуществующую строку. Ответ «залочить» показывает, что человек считает блокировки свойством запроса, а не данных.
  - *«Почему проверки в коде мало?»* TOCTOU: две параллельные проверки увидят пустоту.
  - *«Бывает ли exactly-once delivery?»* Нет. At-least-once delivery + idempotent consumer, снаружи выглядит как exactly-once. Тот же приём понадобится для Kafka.

## Блокировки, которые никто не писал: `FOR UPDATE`, `UPDATE`, `INSERT`

Главный вывод дня, шире идемпотентности: **блокировку берёт операция, а не только явная команда.** За Day 3–4 закрепилась привычка «lock = я написал `FOR UPDATE`». На самом деле замки раздаются сами.

### Какая операция что берёт

| Операция | Что берёт на строке |
|---|---|
| `SELECT` (обычный) | ничего — MVCC, читает свою видимую версию |
| `SELECT ... FOR KEY SHARE` | слабейший: «не меняйте ключ этой строки» |
| `SELECT ... FOR SHARE` | «не меняйте строку», но читать с тем же режимом можно |
| `UPDATE` неключевых колонок | `FOR NO KEY UPDATE` — **неявно, сам** |
| `UPDATE` ключевых колонок / `DELETE` | `FOR UPDATE` — **неявно, сам** |
| `SELECT ... FOR UPDATE` | то же самое, но явно и без изменения данных |
| `INSERT` строки с FK | `FOR KEY SHARE` на **родительской** строке |
| `INSERT` в unique-индекс | ничего не блокирует, но может ждать **транзакцию** конфликтующего |

Отсюда `UPDATE ... SET balance = balance - 100` работал в Day 2 без единого `FOR UPDATE`: замок там был, просто неявный. А `SELECT ... FOR UPDATE` нужен ровно тогда, когда между чтением и записью есть логика в Java — надо держать строку в промежутке.

### Матрица конфликтов (кто кого ждёт)

```
запрашиваю ↓ / уже держат →   KEY SHARE   SHARE   NO KEY UPDATE   UPDATE
FOR KEY SHARE                     ок        ок          ок        ЖДЁТ
FOR SHARE                         ок        ок        ЖДЁТ        ЖДЁТ
FOR NO KEY UPDATE                 ок      ЖДЁТ        ЖДЁТ        ЖДЁТ
FOR UPDATE                      ЖДЁТ      ЖДЁТ        ЖДЁТ        ЖДЁТ
```

Проверил руками на `uniq-demo`. Сессия A держит `UPDATE acc SET balance = 500` (то есть `FOR NO KEY UPDATE`), сессия B пробует разное:

```
SELECT id FROM acc WHERE id = 1                      Time:    40.903 ms   ← MVCC, не ждёт
SELECT id FROM acc WHERE id = 1 FOR KEY SHARE        Time:     2.639 ms   ← совместимы
INSERT INTO child (acc_id) VALUES (1)                Time:     7.414 ms   ← FK-вставка не ждёт!
SELECT id FROM acc WHERE id = 1 FOR SHARE            Time: 16801.275 ms   ← ждал до COMMIT A
```

Третья строка — это и есть объяснение `for no key update` из Day 4: пока мы двигаем `balance`, другая транзакция может спокойно вставлять строки, ссылающиеся на этот счёт, потому что `id` мы не трогаем. Если бы Hibernate брал полный `for update`, любая вставка в `transfers` во время перевода вставала бы в очередь.

### Почему `INSERT` — особый случай

`FOR UPDATE` означает «вот существующая строка, захватываю её». При `INSERT` захватывать **нечего**: строки ещё нет.

| | `SELECT ... FOR UPDATE` | `INSERT` в unique-индекс |
|---|---|---|
| что блокируется | существующая строка | ничего: строки ещё нет |
| кто инициатор | я захватываю | я лишь создал конфликт для других |
| кто ждёт | все, кому нужна строка | только тот, кто вставляет **то же значение** |
| на чём висит ожидание | строка (`tuple`) | **`transactionid`** чужой транзакции |
| зачем ждёт | получить **доступ** | узнать **вердикт** (и обычно это ошибка) |

### Нельзя заблокировать то, чего нет

```sql
SELECT * FROM transfers WHERE idempotency_key = X FOR UPDATE;   -- ноль строк = ноль замков
IF not found THEN INSERT ...                                    -- обе транзакции сюда дойдут
```
Две параллельные проверки увидят пустоту и обе вставят. Это и есть корень TOCTOU: **у отсутствия строки нет замка**.

Кто умеет столбить несуществующее значение:

1. **`UNIQUE` индекс** — наш выбор. Столбит самим фактом вставки, работает даже для запросов мимо нашего кода.
2. **Advisory lock** — `SELECT pg_advisory_xact_lock(hashtext(key))`: замок по произвольному числу, вообще не привязан к данным, держится до конца транзакции. Когда уникального индекса не сделать.
3. **`SERIALIZABLE`** — умеет отслеживать ещё не существующие строки (predicate locks), но платишь откатами всей нагрузки.

### Как смотреть это в проде

```sql
-- кто ждёт и чего
SELECT pid, state, wait_event_type, wait_event, query FROM pg_stat_activity
WHERE wait_event_type = 'Lock';

-- кто кого держит (сразу отвечает на «кто виноват»)
SELECT pid, pg_blocking_pids(pid), query FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- незанятые запросы блокировок
SELECT pid, locktype, transactionid, relation::regclass, mode, granted FROM pg_locks WHERE NOT granted;
```

`wait_event`: `transactionid` — ждём завершения чужой транзакции (уникальный индекс, конфликт версий); `tuple` — ждём конкретную строку; `relation` — ждём таблицу целиком (`ALTER TABLE`, `VACUUM FULL`).

Ручки: `lock_timeout` (сколько ждать чужой замок, потом ошибка), `deadlock_timeout` (через сколько искать цикл, по умолчанию 1 с), `statement_timeout` (общий предел на запрос). В банке `lock_timeout` обычно ставят явно — лучше быстрая ошибка, чем зависший на минуту перевод.

### Что это даёт на интервью

- *«Берёт ли `UPDATE` блокировку без `FOR UPDATE`?»* Да, `FOR NO KEY UPDATE` на строке, до конца транзакции.
- *«Зачем тогда `FOR UPDATE`?»* Чтобы держать строку в промежутке между чтением и записью, когда решение считается в приложении.
- *«Может ли `INSERT` заблокироваться, если я ничего не лочил?»* Да — на уникальном индексе, ждёт `transactionid` конфликтующей транзакции.
- *«Как заблокировать строку, которой ещё нет?»* Никак: `UNIQUE`, advisory lock или `SERIALIZABLE`.
- *«Блокирует ли чтение запись?»* Нет, MVCC — но `FOR SHARE`/`FOR UPDATE` уже не обычное чтение.

## Эксперимент в psql: как именно ждёт `INSERT`

Одноразовый Postgres 17 в Docker (контейнер `uniq-demo`), данные MiniBank не трогал.

**1. Строка существует до `COMMIT`, но видит её только автор.**
```
[A] BEGIN; INSERT INTO transfers ... ;
[A]  xmin | xmax | id | idempotency_key | amount
[A]   740 |    0 |  1 | 1111...         | 200000     ← A видит

[B] SELECT count(*) FROM transfers;  →  0           ← B не видит
```

**2. Конкурирующий `INSERT` висит до конца чужой транзакции.**
```
A: COMMIT через 30 с  →  [B] ERROR: duplicate key ...   Time: 25102 ms
A: ROLLBACK через 8 с →  [B] INSERT 0 1                 Time:  5916 ms
```
Один и тот же запрос с одними и теми же данными даёт разный результат — решение принимала не B, а исход A.

**3. На чём висит — видно в `pg_locks` (locktype `transactionid`, не строка!).**
```
 pid |   locktype    | transactionid |     mode      | granted
-----+---------------+---------------+---------------+---------
 276 | transactionid |           757 | ExclusiveLock | t        ← A держит замок на самой себе
 291 | transactionid |           758 | ExclusiveLock | t        ← B тоже на себе
 291 | transactionid |           757 | ShareLock     | f        ← B ЖДЁТ транзакцию A
```
```
 pid | wait_event_type |  wait_event   | query
 291 | Lock            | transactionid | INSERT INTO transfers (idempotency_key, amou
```
Приём: каждая транзакция при старте берёт `ExclusiveLock` на собственный номер и держит до конца. Тогда «подожди, пока 757 закончится» решается без новых сущностей — встань в очередь за этим замком. Завершилась любым способом → замок свободен → ждущий проснулся.

**Оговорка про тест:** `concurrentDuplicatesAreAppliedOnce` доказывает **результат** (деньги двинулись один раз), но не **механизм** — из него не видно, что неудачники ждали на индексе. Это видно только в psql. Тест и эксперимент дополняют друг друга.

- [ ] **Записывать ли неудачные попытки.** Сейчас при `InsufficientBalanceException` откатывается вся транзакция вместе с `INSERT` — записи не остаётся, повтор попробует снова. Поэтому колонки `status` в `V2` нет: она могла бы хранить только `'SUCCESS'`. Чтобы хранить исход, нужна вторая транзакция (`REQUIRES_NEW`).
- [ ] **Безопасность: скоуп ключа по владельцу.** Сейчас, прислав чужой ключ, можно получить в ответ чужой перевод (кто, кому, сколько). Нужен `UNIQUE (user_id, idempotency_key)` или проверка владельца при возврате. Аутентификации в MiniBank пока нет.
- [ ] Deduplication window: таблица ключей растёт вечно, сколько хранить и чем чистить?
- [ ] Где хранить ключи — Postgres или Redis? Что ломается, если Redis потерял ключ.
- [ ] **Метрика «доля запросов, отбитых по дублю»** — у живого мобильного клиента она никогда не ноль (сети рвутся всегда). Резкое падение в ноль после релиза приложения = клиент сломал генерацию ключа. Ловится за часы, а не за месяц.
- [ ] **Эвристика-алерт:** одинаковый payload с разными ключами в интервале секунд → сигнал на разбор, **не** блокировка. Запрос для ручной сверки: `GROUP BY from, to, amount, date_trunc('minute', created_at) HAVING count(*) > 1`.
- [ ] **Убрать возможность ошибиться:** не «написали в доках, что надо слать ключ», а SDK/обёртка, где ключ генерится правильно и клиентский разработчик не пишет эту строку руками (так делает Stripe). Если ошибиться можно — кто-нибудь ошибётся, вопрос только когда.
- [ ] **Сторно (компенсирующая транзакция).** Закоммиченный дубль нельзя «отменить» — только новый перевод в обратную сторону со ссылкой на исходный. Понадобится колонка `reverses_transfer_id` (сейчас её нет намеренно: не добавляем колонку под фичу, которой нет).
- [ ] Двухфазная схема `POST /transfers/init` — когда понадобится хранить payload до проведения.
- [ ] Мост к Kafka: exactly-once delivery не существует, есть at-least-once + idempotent consumer — тот же приём.
- [ ] HTTP-слой всё ещё отдаёт `500`: `InsufficientBalanceException`, `IdempotencyKeyConflictException`, `amount <= 0`, `fromId == toId`, несуществующий счёт. Нужен `@RestControllerAdvice` + Problem Details.
