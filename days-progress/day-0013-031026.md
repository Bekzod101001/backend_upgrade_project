## Разобрался

### MCP — протокол, не софт и не ИИ

MCP (Model Context Protocol) — открытый протокол Anthropic, который стандартизирует подключение AI-приложений (host) к внешним инструментам/данным. Транспорт — JSON-RPC 2.0 поверх stdio (локально) или HTTP/SSE (remote). Сервер объявляет **tools** (функции), **resources** (данные для чтения), **prompts** (шаблоны); host через `list_tools` узнаёт, что доступно.

Главная путаница, которую расчистили: **MCP-сервер — не ИИ**. Весь "интеллект" в цепочке происходит ровно один раз — когда модель превращает мутный человеческий текст в точный структурированный вызов (`tool_use` блок с именем tool и заполненными по JSON Schema аргументами). Это не keyword-matching, а семантическое решение модели за один forward pass, потому что список доступных tools (имя+описание+схема) лежит у неё в контексте. Всё, что происходит после этого момента — MCP client → MCP server → реальный API (Jira/Gmail) → ответ — обычный детерминированный код, без какого-либо понимания языка.

### Модель как чистая функция, host — как единственный держатель состояния

Модель — `context → text`, без памяти между вызовами и без доступа к миру. Она не может сама читать файлы или дёргать API — только сгенерировать текстовое "намерение". Host на каждый запрос заново пересобирает: историю диалога + system prompt + список tools — и шлёт одним payload'ом. Отсюда и сама идея tool calling: после реального исполнения tool (file read, API call) host добавляет результат как `tool_result` в историю и **шлёт её заново** модели — следующий шаг решается с нуля, глядя на весь накопленный контекст.

Из этого же вытекает разница **host vs агент**: host — любая обвязка вокруг модели (даже без цикла, одна кнопка "перевести текст"). Агент — частный случай host'а, где модель сама управляет циклом "вызвал tool → увидел результат → решил дальше" без жёстко прописанного разработчиком сценария (в противовес workflow — где цепочку шагов фиксирует код, модель только заполняет содержимое).

### Авторизация в MCP — два независимых слоя

1. **host ↔ MCP-сервер.** Для stdio (локальный процесс) — авторизации в сетевом смысле нет, это просто доверие к тому, что сам запустил. Для remote/HTTP — OAuth 2.1 + PKCE: discovery auth-сервера → браузерный login/consent → `authorization code` → обмен на `access_token`/`refresh_token` → `Bearer` на каждый запрос. Ровно это и есть то, что в system-reminder сессии выглядит как "servers require authentication before their tools can be used" (Gmail/Calendar/Atlassian) — сессия non-interactive, не может открыть браузер для шага login.
2. **MCP-сервер ↔ реальный backend API** (Jira и т.п.) — либо свой отдельный service-account токен, либо **token passthrough** (сервер пробрасывает тот же токен юзера дальше) — явно описанный в MCP security spec анти-паттерн, частный случай **confused deputy problem**: если `aud` (кому предназначен токен) не проверяется, скомпрометированный сервер может утащить доступ дальше, чем предполагалось.

### Чем больше MCP, тем тяжелее и "глупее" запрос — и как с этим борются

Два разных эффекта от роста числа подключённых tools:
- **Токены** — т.к. модель stateless, полный список tool-схем едет в каждый запрос заново; больше серверов = больше токенов на пустом месте.
- **Точность выбора** — чем больше похожих по смыслу tools, тем выше шанс модели выбрать не тот (needle in haystack среди кандидатов), не только дороже, а хуже по качеству.

Решения: (а) scope на уровне проекта/задачи — не подключать то, что не нужно для текущего контекста (`.mcp.json` per-project); (б) lazy discovery через meta-tool — вместо того чтобы грузить все схемы сразу, держать один лёгкий "search_tools"-тул, а полные схемы подгружать по запросу. Именно это — `ToolSearch`, который видел вживую в этой сессии: закрывает проблему "курица и яйцо" (модель не может запросить то, о чём не знает) через отдельный, всегда загруженный, поисковый слой — RAG-паттерн применительно к каталогу tools.

### Протокол — общий паттерн, не MCP-специфичный термин

Литмус-тест: протокол нужен, когда **две независимые стороны, не видящие код друг друга, заранее договариваются о формате+порядке+смысле сообщений** — так, что реализации можно писать независимо (разные команды, разные языки) и они всё равно поймут друг друга. Примеры из своего стека: HTTP, TCP/IP, TLS, Postgres wire protocol, RESP (Redis), Kafka protocol, AMQP, JSON-RPC (на нём построен MCP), OAuth 2.1. Протоколы слоятся — HTTP поверх TCP поверх IP, MCP (JSON-RPC + методы типа `tools/call`) поверх stdio/HTTP/SSE — каждый слой договаривается только о своей части, не лезет во внутренности соседнего (encapsulation).

Не протокол: сигнатура метода внутри одного процесса (просто API/интерфейс, нет сериализации "по проводам") и формат данных в покое (CSV и т.п. — формат, не протокол, протокол подразумевает взаимодействие/handshake).

### JDBC-драйвер — не протокол, а три разных слоя под одним названием

- **JDBC (спецификация)** — Java-only интерфейсы (`Connection`, `Statement`), in-process API-контракт, аналог SPI. Не протокол.
- **JDBC-драйвер** (`pgjdbc`) — конкретная реализация этого API, обычная библиотека.
- **Postgres wire protocol** — то, что драйвер реально шлёт по сети серверу Postgres. Вот это протокол. Доказательство: `psycopg2` (Python, вообще без JDBC) и `pgjdbc` (Java) — разный код, разные языки, но оба говорят с одним Postgres-сервером, потому что оба независимо реализуют один и тот же wire protocol.

Поправка к более ранней (упрощённой) аналогии "MCP как JDBC": точнее — MCP protocol (JSON-RPC spec) соответствует Postgres wire protocol (реальный контракт по сети), а MCP SDK соответствует `pgjdbc`/`psycopg2` (языко-специфичная библиотека, реализующая протокол за тебя).

### REST API vs протокол

REST API не стоит в одном ряду с протоколом — он построен **на базе** протокола (HTTP). Критерий различия — не "кто придумал формат", а **сколько независимых сторон это стандартизировали**:
- HTTP — зафиксирован в RFC, соблюдается тысячами несвязанных реализаций (каждый браузер, каждый веб-сервер) — переписать по-своему нельзя, никто не поймёт.
- Конкретный REST API (`TransferController`) — одноразовый контракт одной команды: форма URL, JSON-тела — чистый произвол автора сервиса, поверх HTTP как транспорта. Consumer обязан прочитать именно эту документацию (Swagger/OpenAPI) и подстроиться — никакого стандарта тут нет.

Сам REST — архитектурный *стиль* (из диссертации Fielding: stateless, resource-oriented URLs, методы по смыслу), а не жёстко проверяемый протокол — можно нарушить половину рекомендаций и API всё равно будет "работать".
