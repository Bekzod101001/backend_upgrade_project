## Конспект: SOLID на практических примерах Java

### Single Responsibility Principle (SRP)

У модуля должна быть одна причина для изменения. Важно: SRP не означает, что класс должен содержать только один метод.

Пример нарушения: `OrderService` рассчитывает стоимость заказа, сохраняет заказ в БД и сам формирует/отправляет email.

Решение: `PriceCalculator` (расчёт стоимости), `OrderRepository` (сохранение), `NotificationService` (уведомления), `OrderService` (координация процесса создания заказа).

Вывод: ответственность определяется причиной изменения, а не количеством методов или зависимостей.

### Open/Closed Principle (OCP)

Сущности должны быть открыты для расширения, но закрыты для модификации.

Пример нарушения: `ShippingService` содержит множество `if/else` для расчёта стоимости разных способов доставки — добавление нового способа требует изменения существующего класса.

Решение: интерфейс `ShippingStrategy`, отдельные реализации стратегий доставки, выбор алгоритма через полиморфизм.

Вывод: расширять поведение можно через интерфейсы, композицию и Strategy Pattern, наследование необязательно. Замена `if/else` на `switch` сама по себе OCP не решает.

### Liskov Substitution Principle (LSP)

Объект дочернего типа должен иметь возможность заменить объект родительского типа без нарушения корректности программы. Переопределять методы разрешено, нарушать контракт — нельзя.

Три правила: (1) нельзя усиливать предусловия; (2) нельзя ослаблять постусловия; (3) нельзя нарушать инварианты.

Пример нарушения: `LockedSavingsAccount` реализует `BankAccount`, но `withdraw()` выбрасывает `UnsupportedOperationException`, хотя контракт предусматривает снятие денег.

Решение: пересмотреть контракт и разделить возможности счетов на специализированные интерфейсы.

Вывод: наследование или реализация интерфейса ещё не гарантирует поведенческую совместимость.

### Interface Segregation Principle (ISP)

Клиенты не должны зависеть от методов, которые им не нужны.

Пример нарушения: `DocumentService` содержит методы `create()`, `edit()`, `delete()`, `print()`, `sign()`, `archive()` — при этом `PrinterService` должен реализовывать все методы, хотя использует только `print()`.

Решение — разделить интерфейсы: `CrudDocumentService`, `PrintDocumentService`, `SignDocumentService`, `ArchiveDocumentService`. Один класс может реализовывать несколько специализированных интерфейсов.

Вывод: интерфейсы проектируются вокруг потребностей клиентов, а не по принципу «один метод — один интерфейс».

### Dependency Inversion Principle (DIP)

Высокоуровневые модули не должны зависеть от низкоуровневых — оба должны зависеть от абстракций.

Пример нарушения: `PaymentService` напрямую зависит от `StripePaymentGateway`.

Решение: интерфейс `PaymentGateway`, который реализуют `StripePaymentGateway` и другие провайдеры; `PaymentService` зависит от `PaymentGateway`.

**DIP vs DI:** DIP — архитектурный принцип, определяющий направление зависимостей; DI (Dependency Injection) — техника передачи зависимостей объекту извне. DI не гарантирует соблюдения DIP — внедрение конкретного `StripePaymentGateway` через конструктор — это DI, но зависимость от конкретной реализации сохраняется.

**Spring:** `@Autowired` — аннотация для внедрения зависимостей (для единственного конструктора необязателен); `@Primary` и `@Qualifier` помогают выбирать между несколькими реализациями.
