## Сделано

Разобрал метод оформления заказа (checkout) с проверкой остатков, списанием баланса и отправкой уведомления. Самостоятельно обнаружил:

- отсутствие валидации входных данных;
- избыточные SQL-запросы внутри циклов;
- отсутствие блокировок при конкурентных запросах;
- риск отправки email до успешного COMMIT;
- необходимость выделения бизнес-логики из контроллера в сервис.

## Разобрался

### Бизнес-инварианты

Инвариант — условие, которое должно оставаться истинным при любых допустимых изменениях состояния системы. Примеры: баланс пользователя не должен становиться отрицательным; остаток товара не должен уходить в минус; одно оформление заказа не должно приводить к повторному списанию денег.

Важно: простая проверка через `if` не гарантирует соблюдение инварианта при конкурентных запросах.

### Concurrency и блокировки

Разобрал применение `SELECT FOR UPDATE` (`lockForUpdate()` в Laravel). Самостоятельно определил:

- для защиты баланса нужно синхронизировать изменения пользователя;
- для защиты остатков — синхронизировать изменения товаров;
- блокировки нескольких ресурсов нужно получать в согласованном порядке (например, по возрастанию ID), чтобы снизить риск deadlock — тот же принцип canonical lock ordering, что уже закрывал в MiniBank на day-0004.

### Атомарный UPDATE

Сравнил два подхода к списанию средств:

- Подход 1: `SELECT FOR UPDATE` → проверка → `UPDATE`.
- Подход 2:
  ```sql
  UPDATE users
  SET balance = balance - 700
  WHERE id = 10 AND balance >= 700;
  ```

Самостоятельно пришёл к выводу, что второй вариант предпочтительнее для простого списания:

- проверка условия и изменение выполняются атомарно;
- требуется меньше SQL-запросов;
- СУБД сама обеспечивает синхронизацию конкурентных обновлений;
- количество изменённых строк позволяет определить успешность списания.

### Идемпотентность

Разобрал проблему повторного HTTP-запроса после успешного COMMIT, когда клиент не получил ответ. Самостоятельно предложил использовать Idempotency-Key вместо поиска похожих заказов за промежуток времени (тот же подход, что уже реализован в MiniBank на day-0005).

Ключевые принципы:

- один логический checkout — один ключ идемпотентности;
- повторный запрос с тем же ключом не должен создавать повторное списание;
- `UNIQUE(user_id, key)` защищает от дублирующих записей;
- проверки существования ключа через `SELECT` недостаточно из-за race condition — нужна корректная обработка конкурентных запросов с одинаковым ключом.
