## Разобрался — что показал checkpoint

### Вопрос 1 (почему concurrency-инструменты, включая SERIALIZABLE, не решают двойное списание при retry) — исходный ответ содержал реальную ошибку про SERIALIZABLE

Мой ответ: «lost update предполагает что одна из транзакций теряется, а повторная экзекуция — что мы делаем одно и то же. SERIALIZABLE нужен, чтобы транзакции одинаково грамотно мержились, но нахуя нам это, нам нужно чтобы наоборот одна отменилась».

**Ошибка:** SERIALIZABLE не «мержит» и не решает, кому отмениться. Он гарантирует только одно — итог будет эквивалентен **какому-то последовательному порядку**, как если бы транзакции выполнились строго одна за другой. Два одинаковых легитимных перевода, выполненных именно так (друг за другом, без наложения), — это УЖЕ валидный последовательный порядок. Если баланса хватает на оба — SERIALIZABLE их спокойно пропустит, ему нечего запрещать, он свою работу выполнил безупречно.

**Ключевая мысль:** у БД нет понятия «повторная попытка» вообще. Она видит только SQL — два синтаксически валидных перевода. Разница между «клиент осознанно перевёл дважды» и «сеть оборвалась и клиент ретраит» существует **только на уровне бизнес-логики** (idempotency key), никогда не выражается в SQL. Отсюда и собственная формула из Day 5, которую стоило вспомнить дословно:
```
убрать конкурентность (1 поток, пауза 30 с между запросами) → баг ОСТАЁТСЯ
убрать retry (1000 потоков, у каждого свой перевод)         → бага НЕТ
```
Значит причина — retry, а не параллельность, и retry может случиться даже строго последовательно, без всякого наложения по времени — там попросту нечего ловить ни одному concurrency-инструменту.

**Итоговая формулировка:**
```
lost update:        аномалия ИЗОЛЯЦИИ, есть имя в стандарте, есть isolation level (SERIALIZABLE), который её запрещает
двойное списание:    НЕ аномалия изоляции вообще — БД работает идеально корректно
```

**Побочный уточняющий вопрос (важная часть разбора):** «а как определяется этот порядок?» — как SERIALIZABLE вообще узнаёт, что порядок нарушен?

Ответ: Postgres использует **SSI (Serializable Snapshot Isolation)**, не классический 2PL. Транзакции выполняются параллельно как обычно (MVCC-снепшоты), порядок никто не строит заранее. В конце Postgres ищет в графе зависимостей конкретный опасный паттерн — цикл из rw-зависимостей между как минимум тремя транзакциями (pivot-транзакция с входящей и исходящей rw-antidependency). Если цикл найден — одна транзакция обрывается (`ERROR: could not serialize access due to read/write dependencies`, SQLSTATE `40001`). Если цикла нет — реальный порядок коммитов уже сам по себе является валидным последовательным порядком, обрывать нечего.

Отсюда и объяснение, почему retry выживает: если повторный перевод пришёл **после** коммита первого (клиент подождал и ретраит) — снепшоты вообще не пересекаются по времени, зависимостей нет, циклу неоткуда взяться. Для SSI это неотличимо от «два разных легитимных перевода одно за другим».

Уточнение по MiniBank отдельно: Postgres даже на `REPEATABLE READ` уже ловит простой write-write конфликт на одной строке (first-committer-wins, `could not serialize access due to concurrent update`); `SERIALIZABLE` добавляет обнаружение более тонких аномалий с 3+ транзакциями. MiniBank работает на дефолтном `READ COMMITTED` + явном `SELECT ... FOR UPDATE` — не на SERIALIZABLE, это разные инструменты для разных задач.

### Вопрос 2 (почему idempotency key генерирует клиент, а не сервер) — верный итог, до которого дошёл сам в разговоре

Рассуждал вслух: первая мысль — «генерить на бэке», затем сам предложил двухфазную схему («сделать перед платежом отдельный запрос на генерацию айдишника, без него не пускать») и сам увидел в ней избыточность («это можно вынести и на фронт, зачем нам запрос»), пришёл к правильному выводу: **ключ генерируется на клиенте, с дополнительной валидацией формата на бэке**.

Ценно: не зная термина, самостоятельно переоткрыл **двухфазную схему (Stripe PaymentIntent)** — `POST /transfers/init` → сервер выдаёт ключ → клиент использует его при реальном платеже. Реальный паттерн, записан ещё в Day 5.

**Чего не хватило:**
1. **Почему сервер в принципе не может сгенерировать ключ сам в одном запросе (без /init).** Ответ: сервер физически не может знать, что входящий HTTP-запрос — повтор предыдущего; это знание существует только у клиента (только он помнит, что уже пытался сделать именно это действие). Если генерировать ключ на каждый входящий запрос — защита эквивалентна её отсутствию.
2. **Конкретный код-пример поломки**, который прямо просил вопрос:
```js
async function submit() {
  const key = crypto.randomUUID();          // ❌ генерируется КАЖДЫЙ РАЗ внутри функции отправки
  ...
}
// сеть оборвалась → повтор submit() → НОВЫЙ ключ на каждый вызов → защита сведена к нулю
```
Фикс — генерировать один раз снаружи цикла попыток:
```js
const key = crypto.randomUUID();          // ✅ один раз — при открытии формы / первом клике
async function submit() { ... }            // тот же ключ при каждом ретрае
```

Отдельно отмечено: предложение про «валидацию формата ключа (не хуйхуй-тест-тест)» — разумная, но отдельная забота (input validation), не отвечает на вопрос «кто и когда генерирует».

### Вопрос 3 (почему retry-обработка должна быть СНАРУЖИ транзакции) — не ответил прямо, но сам задал ключевой вопрос и дошёл до сути

На прямой вопрос не ответил, вместо этого спросил: «а зачем ретраить внутри транзакции, если нужно сначала ревертнуть все изменения?» — это и есть верный инсайт, только в форме вопроса, а не утверждения.

Разобрали механизм полностью: в Postgres как только **любой** оператор внутри транзакции падает (например, unique violation), **вся транзакция целиком** переходит в состояние **aborted** — любой следующий запрос в этой же транзакции, даже безобидный `SELECT`, тут же получает `current transaction is aborted, commands ignored until end of transaction block`. Поймать исключение Java-кодом — не то же самое, что откатить транзакцию на уровне БД; сессия остаётся aborted, пока не случится explicit `ROLLBACK`, а он происходит автоматически только когда `@Transactional`-метод целиком завершается с исключением (AOP-прокси, Day 8).

Отсюда разделение на два бина:
```
TransferExecutor.execute()  — @Transactional: save() падает → исключение улетает НАРУЖУ → ROLLBACK, транзакция закрыта
TransferService.transfer()  — БЕЗ @Transactional: ловит исключение УЖЕ ПОСЛЕ гарантированного rollback,
                               findByIdempotencyKey() — это НОВАЯ, чистая транзакция
```
Финальное подтверждение своими словами: «получается перед тем как ретраить нам нужно откатить изменения» — верно, вопрос закрыт через диалог, а не с первой попытки.

### Вопрос 4 (одинаковый payload/разные ключи vs одинаковый ключ/разный payload) — первая половина твёрдая, вторая доведена через уточняющий вопрос

**Часть А (разные ключи, одинаковый payload) — верно:** «оба перевода пройдут». Аргумент против дедупликации по содержимому построен самостоятельно и правильно: предложил и сам же отверг эвристику «одинаковый payload в окне 100 мс = дубль» вопросом **«откуда нам знать, может это с другого клиента запрос, или автоплатёж»** — дословно воспроизвёл рассуждение из собственных заметок Day 5 про natural idempotency и неразличимость payload по содержимому, не заглядывая в файл.

**Часть Б (тот же ключ, разная сумма) — верный инстинкт, но не сам объяснил «почему».** Сказал: «не пропускаем такую транзакцию», это верно. Но на вопрос «почему нельзя молча проигнорировать, хотя бы дать понять клиенту, что по такому ID уже выполнена транзакция» — сам не ответил, потребовалось разъяснение:

Разница между двумя случаями:
```
СЛУЧАЙ A (истинный дубль): ключ K, payload ИДЕНТИЧЕН → молча вернуть success = ПРАВДА (уже реально случилось)
СЛУЧАЙ B (конфликт):       ключ K, payload ДРУГОЙ    → молча вернуть success = ЛОЖЬ
                           (900к никогда не двигались, а клиент подумает, что перевод состоялся)
```
Сервер не может сам решить, какая версия правдива (баг клиента или исправленная попытка) — это решение человека, не бэкенда, поэтому единственный корректный ответ — громкая ошибка с обеими версиями payload (`IdempotencyKeyConflictException`, уже есть в коде; пока отдаётся как некрасивый `500`, TODO — `409 Conflict`).

Связка с Day 6: этот случай — чистый **KNOWN FAILURE** из формулы `SUCCESS / KNOWN FAILURE / UNKNOWN`. Known failure полагается сообщать явно; молчать полагается только про UNKNOWN. Хорошая находка — сам не связал эти два блока, пришлось подсветить явно.
